# 时叙三端与连锁运营系统审计

审计日期：2026-10-30。结论针对当日工作区源码及本地隔离验证，不是线上渗透测试、合规认证或上线批准。

## 1. 管理结论

**当前应定位为“已有真实数据库的本地集成系统”，不能认定为可放心营业的连锁管理系统。** 不是全部没做，也不是全靠内存；真正的问题是业务闭环不完整、状态与权限边界有漏洞、外部能力仍为替身，以及验收标准把“页面存在、构建成功、测试通过”误当成经营正确。

最重要的纠偏：之前“全栈完成”“测试全绿”等表述，不能继续被引用为生产成熟度证明。删除演示文案、配置 AppID、生成 mp-weixin 包、定义支付接口，均不等于完成微信身份、真实收款或设备交付。

无需推翻现有 UI，也无需立刻拆微服务。建议保留三端与模块化单体，先修安全和交易不变量，再补运营闭环，最后做授权的渠道联调和试营业验收。

### 目前确实有的基础

- 正式工程为 `apps/server`（NestJS＋Prisma＋SQLite）、`apps/admin`（总部与门店统一后台）、`apps/miniprogram`（uni-app），共享规则与外部适配层独立在 `packages`。历史 demo、旧 Fastify 工程不计入当前完成度。
- 门店、商品、分类、座位、渠道、库存、订单、订单行、杯贴、费用、审批和流水有数据库实体及写入链路，不是仅浏览器变量。见[数据库模型](/Users/th/Desktop/Full愈-时叙/apps/server/prisma/schema.prisma#L23)。
- 服务端重新计算价格，有历史单价/成本快照；扣库存已有条件更新和事务；销售台账有唯一去重键。这些应该保留，而不是误报为“完全没有事务/幂等”。
- 员工禁用后，守卫每次读取当前账号状态；资料新接口使用登录身份；错误过滤器对未知错误不直接返回堆栈。
- 购物袋、备注、筛选、POS 草稿和最近订单入口已有本地持久化；最近订单只保存 ID 再读取服务端。**本地草稿不是订单事实**，不应为了“全部持久化”把所有临时 UI 状态都塞进数据库。
- live 模式缺少 provider 时会报错，不会自动偷偷回落 mock；问题在于 live 实现尚空、生产环境缺配置仍默认选择 mock。

## 2. 评级规则

- **P0**：接入真实顾客、真实资金或连锁营业前必须消除的阻断项。不是说当前已经发生线上损失。
- **P1**：高优先级，受影响功能在试营业前补齐；若暂不做，必须明确停用该功能并说明限制，不能默默交付。
- **P2**：一般功能/易用性缺口，仍须给验收口径。
- **动态**：本次实际执行得到结果；**静态**：源码明确存在断点；**静态竞态**：可构造危险交错，但本次未并发复现；**能力缺口**：在指定代码范围内未找到完整链路，不等于其他系统也没有。

以下每项整改均为建议，**本次没有执行业务修复**。UI-10 与 TX-10、UI-11 与 TX-13 是同一根因，已合并，不重复计数。

## 3. 身份、权限与信息边界

### SEC-01｜P0｜仅凭会员码取得他人顾客会话

- **证据/确认方式**：动态。[session 入口](/Users/th/Desktop/Full愈-时叙/apps/server/src/auth/auth.controller.ts#L38)无身份校验；[resolveCustomer](/Users/th/Desktop/Full愈-时叙/apps/server/src/auth/auth.service.ts#L116)按会员码找到客户即返回并签发令牌。探针取得同一客户 ID，修改资料 HTTP 200，原会话看见改名。
- **触发与影响**：知道他人用于展示或扫码的会员码即可冒用会话。会员码是标识，不是认证凭证。
- **最小整改**：会员识别与登录认证分离；已有顾客会话只能经可信微信身份或明确认证流程签发，旧受影响会话评估撤销。不能只把码变复杂。
- **验收**：A 持 B 的会员码不能登录 B、读 B 订单或改 B 资料；有效微信身份仍可恢复自己的账号。现有“会员码恢复会话”测试必须按安全规则更正，不能保留错误预期。

### SEC-02｜P1｜公开顾客目录暴露商品成本字段

- **证据/确认方式**：动态。[mapProduct](/Users/th/Desktop/Full愈-时叙/apps/server/src/common/mappers.ts#L42)复用内部字段；[public bootstrap](/Users/th/Desktop/Full愈-时叙/apps/server/src/api/customer.controller.ts#L62)直接返回。未登录 fresh 商品存在 `costCents`；本次 retail 返回中未发现该字段，不能扩大结论。
- **触发与影响**：无需员工权限即可获知内部成本；成本是否显示在页面无关紧要，接口已经返回。
- **最小整改**：公共 DTO、员工 DTO、财务 DTO 分离，白名单输出；并检查顾客订单中的成本映射。
- **验收**：匿名和顾客目录/订单响应不含成本、内部利润及不必要内部字段，授权财务端仍可查看。

### SEC-03｜P1｜重置员工密码不撤销旧令牌

- **证据/确认方式**：动态。[员工守卫](/Users/th/Desktop/Full愈-时叙/apps/server/src/auth/staff.guard.ts#L24)核验账号活跃状态，但无会话版本/撤销检查。隔离库换密码哈希后，旧令牌调用 `/auth/me` 仍为 200。
- **触发与影响**：密码泄露后仅重置密码，旧会话仍可继续使用直至到期。禁用账号的立即失效是已实现的另一条控制。
- **最小整改**：定义会话生命周期、强制退出和密码变更撤销策略，使用持久会话版本或等效机制。
- **验收**：重置密码、主动撤销、账号禁用、调店后，旧令牌按既定策略失效或失去原范围；不能只测试新密码登录。

### SEC-04｜P0｜空门店授权被解释为不限制门店

- **证据/确认方式**：动态。[store/orders](/Users/th/Desktop/Full愈-时叙/apps/server/src/api/store.controller.ts#L74)把 `staff.storeIds` 传入，[listOrders](/Users/th/Desktop/Full愈-时叙/apps/server/src/orders/orders.service.ts#L448)仅在数组非空时加范围条件。探针保留查看权限、清空门店授权且 `allStores=false` 后，HTTP 200 返回了 3 个不属于其授权范围的合成订单。
- **触发与影响**：新建未分配门店、撤销最后一个门店、异常配置时，账号反而可看订单。
- **最小整改**：用明确的 ALL / NONE / STORES 范围类型；NONE 必须拒绝或空结果，不得等于 ALL。审计所有用“空数组省略 where”的财务、审批、订单入口。
- **验收**：有权限但零门店、单店、多店、全店分别测试列表/明细/汇总/导出；零门店永远不能扩大权限。

## 4. 交易、履约与资金一致性

### TX-01｜P0｜微信预支付传入内部顾客 ID 而非 openId

- **证据/确认方式**：静态。[prepay](/Users/th/Desktop/Full愈-时叙/apps/server/src/api/customer.controller.ts#L140)传 `openId: customer.id`，而[客户模型](/Users/th/Desktop/Full愈-时叙/apps/server/prisma/schema.prisma#L179)另有 `openId`。
- **触发与影响**：mock 可掩盖身份字段混淆，换成真实 provider 后无法正确绑定微信付款身份。
- **最小整改**：读取已验证、属于当前客户的渠道身份；缺失时阻止预支付，不把内部 ID 当渠道 ID。
- **验收**：内部 ID 与 openId 不同的用例正确传参；未绑定、错误 app 身份拒绝；获授权后再做渠道沙箱与真机验证。

### TX-02｜P0｜创建订单和收款缺少贯穿重试的业务幂等

- **证据/确认方式**：静态。[createUnpaidOrder](/Users/th/Desktop/Full愈-时叙/apps/server/src/orders/orders.service.ts#L175)每次新建 ID、先预扣库存；[createOrder](/Users/th/Desktop/Full愈-时叙/apps/server/src/orders/orders.service.ts#L404)随后 charge，未对抛出的超时/结果未知形成可恢复状态。
- **触发与影响**：用户重复提交、网络断开后重试可生成不同订单；网关已收款但响应丢失不能安全地简单“重付”。抛异常可能留下占库未付单。
- **最小整改**：创建意图持久化、请求幂等键＋请求内容指纹、支付尝试记录；区分失败/处理中/未知；通过查询和补偿收敛。已有 SALE 去重只保护同一订单流水，不保护重复建单。
- **验收**：同键同内容返回同单；同键异内容冲突；提交响应丢失、网关超时、进程重启后不重复扣款，库存最终可解释。

### TX-03｜P0｜迟到支付成功复活已释放库存的订单

- **证据/确认方式**：动态服务序列。[markPaymentFailed](/Users/th/Desktop/Full愈-时叙/apps/server/src/orders/orders.service.ts#L349)退库存并取消；[markPaid](/Users/th/Desktop/Full愈-时叙/apps/server/src/orders/orders.service.ts#L279)只拦已 paid，不拦取消。探针失败后库存回到原值，随后成功处理使订单 pending/paid，库存仍在原值。
- **触发与影响**：乱序、延迟消息造成有订单无对应库存占用。反向交错也需检查，不能由晚到失败覆盖成功。
- **最小整改**：支付/订单/库存状态机与条件迁移；取消后实际收款走明确的退款或重新占用策略，不能悄悄复活。
- **验收**：成功→失败、失败→成功、重复、取消→成功、并发交错都保持资金库存不变量；真实回调另行验签/金额/商户身份验收。

### TX-04｜P0｜退款先调用外部，再校验本地余额且每次换新退款号

- **证据/确认方式**：静态。[executeRefund](/Users/th/Desktop/Full愈-时叙/apps/server/src/orders/orders.service.ts#L832)新建 RF，先 provider.refund，再在事务中检查剩余金额、累加行退款数量；未在执行阶段以新鲜行状态条件占用可退数量。
- **触发与影响**：外部已退款、本地事务失败或两个旧报价并发，会造成外部资金与账不一致；重试新 RF 不能保证渠道幂等。本次没有真实退款或并发超退证据。
- **最小整改**：先持久化并原子占用退款意图/数量，稳定 refundId；外部执行有状态查询与重试，最终确认后记账。跨系统不是一个数据库事务能解决的。
- **验收**：两人退同一行、同一 refundId 重试、外部成功本地失败、外部未知、部分退款多次累计，均满足数量和金额上限，账与渠道可核对。

### TX-05｜P1｜部分退款没有撤销对应杯的履约资格

- **证据/确认方式**：动态。[退款处理](/Users/th/Desktop/Full愈-时叙/apps/server/src/orders/orders.service.ts#L865)只有整单全退才标记未扫码杯；[扫码](/Users/th/Desktop/Full愈-时叙/apps/server/src/orders/orders.service.ts#L521)按杯状态执行。两杯退一杯，探针仍将两杯全部扫码，剩余付费数量为 1、已扫码数量为 2。
- **触发与影响**：库存/成本已冲回却仍能制作交付已退杯。
- **最小整改**：行退款与具体履约单位建立对应；制作状态按实际单位判断，原子撤销未制作杯，重打也只包含有效杯。
- **验收**：同款两杯退一杯、不同款部分退、部分已制作、重复扫描、退款与扫描并发，杯数、库存、成本、可履约数一致。

### TX-06｜P1｜打印有持久任务，但缺少可靠投递闭环

- **验收**：重复回调只生成原始任务一次；在提交、领取、设备成功、回写各点中断可恢复；人工补打单独可审计。

### TX-07｜P1｜零售订单可收款而没有可领取库存保障

## 10. 推荐整改次序与退出条件

1. **第一关：身份和边界**。SEC-01/04、OPS-01/02 优先；同时关闭暴露成本、错误成功提示与不可靠外部能力。退出条件：未经授权无法冒用或扩大范围，缺关键配置不运行营业路径。
2. **第二关：一笔钱、一杯茶、一件货**。以创建→支付→制作/领取→退款→库存→流水为一个项目，修 TX 系列和 UI-01/05。先持久状态和故障测试，再 UI 接线；P0/P1 不能只修 happy path。
3. **第三关：运营配置与两端同步**。按配置清单补消费端、版本、错误态、分页、草稿隔离；用新门店、新商品、非默认规则验收，保留既有视觉。
4. **第四关：连锁经营闭环**。采购/库存凭证、跨店履约、对账关账、组织范围。业务有分歧时只问经营决策，不让用户补技术漏项。
5. **第五关：授权试点**。真实渠道/真机/设备、备份恢复与告警先验证；试点做一个完整营业日及跨日/退款/关账演练，再讨论多店推广。未授权不得接真实系统或改线上。
