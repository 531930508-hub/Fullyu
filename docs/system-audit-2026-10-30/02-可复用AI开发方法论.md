# 面向长期运营的 AI 全栈开发方法论

适用：小程序/顾客端＋门店工作台＋总部后台＋服务端，尤其涉及多店、库存、收退款、会员、审批与财务的系统。不是特定框架教程，也不是要求每个项目重建 ERP。

## 核心规则

**交付单位是“一个可验证、可恢复的业务闭环”，不是页面、接口、数据库表或测试数量。**

一个功能至少回答：谁配置 → 谁使用 → 后端怎么授权和校验 → 真数据存哪 → 再次进入如何读回 → 历史如何保留 → 失败如何恢复 → 怎么独立证明正确。

AI 主动完成技术完整性检查；用户负责重要经营决策，不负责提醒“别写死”“记得落库”“加权限”“异常怎么办”。普通工程默认项自行按规范处理，影响价格、权益、结算、采购职责、数据归属等决策才集中提出。

这些规则降低遗漏，不能保证任何 AI 绝不犯错。必须结合自动化门禁、独立验收和真实运行证据；不能用长提示词代替工程控制。

## 1. 先确定任务类型和边界

### 审计/咨询

只读调查、证据和建议；可创建用户要求的报告与隔离测试材料，不擅自改业务、权限、数据库、上线环境。发现严重问题也不是自动修生产的授权。

### 小修复

简短写明根因、受影响链路、最小修改和回归验收即可。先有能失败的复现，再修根因，再证明通过。不要为小修复强行做完整产品文档或数轮子代理评审。

### 新功能/多端改造

先形成简短功能契约及影响矩阵；现有设计为基线。需求清楚时按合理默认推进，不反复问“是否继续”。真正影响经营口径的未知点先说明并确认。

### 发布/真实集成

独立授权，不被“写完代码”“生成交付包”隐含覆盖。变更 schema、真实权限、真实支付、生产数据、公开发布、发消息、上传内部资料各自按授权范围执行。

## 2. 开始前：找准权威工程与真实状态

AI 必须确认当前正式源码、历史 demo、部署目标、数据库类型、构建脚本、现有设计基线和约束。查看项目规则和相关文件，不能在错误旧工程上实现后称完成。

记录当前可运行证据、已有缺陷和未授权事项。命令名称不是安全保证：执行 test/build/deploy 前阅读脚本，避免测试触碰业务库、构建脚本夹带上传或部署。

跨项目参考只复用经过核证的模式，不复制整个旧系统的安全假设、业务参数、凭证、旧视觉或不适用权限。

## 3. 用纵向切片替代“前端做完再说”

每个切片覆盖下表。没有某一层时填写“不适用＋原因”，不能留空。

| 层 | AI 必须给出的答案 | 最低证据 |
|---|---|---|
| 经营目的 | 谁在什么场景完成什么任务，成功与失败分别是什么 | 业务验收句子 |
| 管理入口 | 谁能修改规则，全球/总部/区域/门店范围如何继承 | 可操作入口或明确固定原因 |
| 顾客/门店入口 | 从哪里进入，加载/空/失败/处理中怎么表现 | 正常与异常界面 |
| API 契约 | 输入、输出、枚举、错误码、分页、金额/日期单位 | 定义＋契约测试 |
| 授权 | 身份、动作、对象、字段、门店及批量范围 | 直接 HTTP 正反用例 |
| 数据 | 权威表、约束、版本、迁移、历史和删除策略 | 新请求读取＋重启后证明 |
| 执行 | 状态机、幂等、并发、外部副作用 | 不变量与故障注入 |
| 运营恢复 | 谁看见失败、谁重试、怎么对账/纠错 | 待办/日志/恢复记录 |
| 交付 | 哪个版本、哪些环境、哪些能力被验证 | 命令输出/截图/脱敏响应 |

禁止用新建空页面、静态卡片、固定数组、成功 Toast、内存 Map 或永久 mock 替代以上证据。

## 4. 配置与常量：不是“所有内容都进后台”

### 必须考虑运营配置的内容

门店信息/开放能力、营业与临时休业、商品价格/可售/选项/描述、库存预警、退款审批、会员权益、报损规则、设备绑定、采购参数、通知模板、财务分类及分摊口径。

判断依据：是否会由经营人员在不发版的情况下调整、是否因门店/时间而不同、是否影响钱/库存/权益。答案为是就要列配置归属和消费链路；不存在后台入口必须解释，而不是藏在源码里。

### 可以保留代码常量的内容

品牌固定标识、已批准设计 token、协议枚举、数学换算、安全不变量、明确不允许运营改变的规则。密钥属于安全配置/密钥管理，不属于普通后台可见业务字段。

### 每个配置的必填字段

所有者；范围/继承优先级；数据类型/单位/校验；默认值的业务来源；管理入口与权限；存储；发布/生效时间；版本；消费者；失效刷新；历史订单使用新值还是快照；修改前后审计；撤销方式。

原则：`门店覆盖 > 区域覆盖 > 总部默认` 只有在业务确认存在相应组织层级时采用，不为了模板硬建区域层。缺值不可导致全权限、免费收款、全员会员或假成功。

**非默认值验收**：新建第三家店、新商品，用从未出现的名称/价格/描述/退款门槛；保存后开启新会话并重启服务再读，最后实际触发规则。只看默认数据正确无法发现写死。

## 5. 四类数据，分别设计持久化

| 数据类别 | 例子 | 权威位置 | 校验方法 |
|---|---|---|---|
| 经营事实 | 订单、支付/退款、库存流水、审批、费用 | 服务端持久库和可追溯凭证 | 新请求、重启、跨设备、恢复后结果一致 |
| 执行状态 | 支付尝试、回调收件、打印任务、重试、幂等键 | 持久任务/数据库；可选队列作运输 | 杀进程后恢复，不重复副作用 |
| 用户草稿 | 购物袋、备注、代点草稿、表单 | 允许设备本地；需要跨设备才服务端 | 账号/门店隔离、TTL、迁移、清理 |
| 展示状态 | 弹窗、选中项、短期加载、排序 | 内存或适当本地缓存 | 不影响金额、身份或最终事实 |

持久化不是“加 localStorage”三个字。草稿要明确键空间（应用/环境/账号/门店/业务），版本、有效期口径、恢复校验、退出与切店策略、成功清理、失败保留。保存越多不一定越好：会员校验结果、收款授权码、令牌等敏感状态不得为了方便无期限缓存。

服务端业务不能依赖某一页面开着、某个进程内 Map、内存锁或用户返回页面触发才能完成。队列也不自动保证可靠：必须能从持久事实恢复任务，消费可安全重复。

历史需要快照的是影响履约/结算的业务版本，例如成交价、优惠依据、商品选项、实际投料及成本口径；不是把所有对象全量复制。配置改动不能悄悄改旧账。

## 6. 权限必须是四维检查，不是隐藏菜单

对每个接口检查：**身份 × 动作 × 对象范围 × 字段范围**。角色有“订单查看”不等于能看所有门店/顾客，更不等于能看内部成本。

- ALL、NONE、明确门店集合分开表示；空授权不默认全量。
- 当前操作者从可信会话取得；会员码、手机号、业务 ID 不自动等于认证凭证。
- 列表、明细、创建、修改、批量导入、导出、统计和后台任务都应用相同范围，不能只保护列表页。
- 更新字段白名单，输出 DTO 分层；隐藏输入框不是防越权，body 自报 id 不是授权。
- 新账号无范围、禁用、改密、调店、权限撤销及旧令牌都要测试。
- 总部采购与门店领用的权限分开；不得因门店工作台需要库存页面就给外部采购权。

测试必须绕过前端直接发 HTTP，使用账号 A 操作 B 的对象。公开接口也要定义可公开字段，不因“有顾客登录”就允许读取商业成本。

## 7. 状态机、不变量与外部副作用

### 最低业务不变量

1. 同一业务意图的重试不创建第二次资金动作；稳定业务 ID 与相同请求内容绑定。
2. 累计退款金额不超过实际可退金额，逐行退款数量不超过可退数量；两者都校验。
3. 一次有效领取只消耗一次库存；已撤销的履约单位不能再出餐/交付。
4. 库存期初＋入库－消耗－损耗±调拨/盘差=期末，差异有凭证，不用直接覆盖掩盖问题。
5. 销售、退款、费用、损耗与报表有统一时间/金额/归属口径；重复消息不重复记账。
6. 审批决定、执行结果、渠道状态彼此可追踪，但不是同一个状态。

### 推荐的责任划分

服务端核价、验证可售与权益→持久化订单/支付意图→调用渠道→校验回调/主动查询→条件推进状态并写财务/库存事实→持久履约任务→设备执行→回写/对账。

这只是职责示意，具体先扣/先占、即时/预售、渠道付款模型按实际契约设计。**禁止在小程序模式里先调用某个“charge成功”再把 JSAPI 当装饰步骤。**

订单、支付、退款、打印、审批、履约各有状态，避免一个 `status` 承担一切。必须存在“处理中/结果未知”的处理方式；超时≠失败，前端弹窗成功≠已到账。

### 三种机制不能混淆

- 数据库事务：同库多项写入一起提交或回滚。
- 幂等：重做同一业务意图不产生第二次业务效果。
- 恢复/对账：外部系统已执行但本地未知时，最终确认和修复状态。

外部支付不能放进本地事务就假装原子；仅生成随机请求号不是重试幂等；仅在一台进程加锁不是多实例安全。条件更新/唯一约束应在实际数据库中落实，任务消费者有领取、租约、重试上限和人工处理渠道。

设备物理打印可能不支持恰好一次。要说明能力边界、稳定任务键、补打标识与人工核对，而不是承诺永不重打。

## 8. 两端一致性与错误诚实性

管理端保存成功必须经过回读，顾客/门店端不能永远显示启动时缓存。定义缓存版本、回前台刷新、下单前重新报价、价格变动再确认。请求乱序必须绑定对象/门店/账号/代次，旧响应不能覆盖最新选择。

前后端响应枚举单一契约、可穷举处理；`approval`、`pending` 不得各写一套。未知枚举要暴露错误，不落到“其他都成功”的分支。

错误态至少区分加载、真实为空、失败、仍显示旧数据。旧数据注明时间和实际条件，不能让筛选标题与导出内容矛盾。订单进度需要主动刷新、轮询或事件更新，并在离开页面时清理资源。

无数据时不塞虚假数字；接口失败不能当零业绩；缺支付参数不能当支付成功；没有权限不能当空白页掩盖。

## 9. 独立验收与证据分级

### 验收先于实现

先用经营规则写 Given/When/Then，再写代码。可以由同一 AI 编写，但预期必须来自独立规范，不能从当前错误实现倒推。修复前看到测试按预期失败，修复后通过；不能删除失败断言来交差。

### 最低测试矩阵

| 维度 | 必测样本 |
|---|---|
| 非默认配置 | 第三家店、新商品、新价格/描述、不同退款门槛 |
| 持久性 | 刷新、关闭重开、重登、服务重启、数据库恢复 |
| 隔离 | 顾客 A/B、员工 A/B、店 A/B、零门店授权 |
| 异常 | 断网、超时、401/403/404/409/500、空结果 |
| 时序 | 双击、重复回调、乱序、延迟、响应丢失 |
| 并发 | 两人审批、两店领取、退款与出餐、导入重复 |
| 故障点 | DB提交前后、渠道已成功但响应丢失、任务领取后进程死 |
| 时间 | 时区、跨日跨月、营业日、TTL边界、权益到期 |
| 规模 | 超过每一个分页/截断边界，历史搜索与总计/导出 |
| 跨端 | 总部改配置→门店/小程序新会话→实际执行→账/库存 |
| 真实能力 | 微信真机、授权渠道沙箱/实物设备，与 mock 结果分别列 |

先从高风险功能选择必要测试，不要求小文案改动跑全部灾备矩阵。钱、身份、库存、权限、审批不得省略对应负向测试。

### 五级证据，不混成一个完成百分比

- E0：只有方案或静态原型。
- E1：源码存在，静态审查/类型/构建证据。
- E2：隔离环境真实数据库＋API/跨端业务闭环通过，外部可能 mock。
- E3：目标部署形态下故障、并发、安全、恢复和容量验证通过。
- E4：经授权的真实集成/真机/试点运营验收通过。

级别按功能记录，不给整个系统强行平均；mock最多证明对应替身契约，不证明真实通道。记录日期、源码版本或校验、命令、退出码、环境、数据隔离方式、产物和未测项。

## 10. 工程门禁与发布

### 代码交付门禁（建议接入 CI，尚未自动部署）

类型/静态检查；相关单测与集成测试；API/枚举契约；权限负向；关键不变量与故障测试；三端所需构建；迁移兼容与数据约束；敏感信息扫描；产物与源码一致性。新依赖确认兼容与供应链风险，不随意引包。

### 真实营业发布门禁

关键配置 fail-closed；真实能力逐项白名单启用；可信健康检查；业务异常告警；备份与恢复演练；迁移/回滚或前向修复方案；业务账库存核对；版本锁定和授权记录。发布之前确认 RPO/RTO、峰值订单量、门店数量和支持响应方式，不无依据许诺 SLA。

SQLite 并非天然不能用。若采用单实例且写量满足、具备备份恢复可以评估；多实例、高并发和共享写入需求需要目标数据库实测。迁移 PostgreSQL/MySQL 也不会自动修复重复退款和权限漏洞。

测试默认使用临时合成数据库；脚本不得隐式使用 shell 中的生产 DATABASE_URL。不得把 live 秘钥、内部财务或原始客户信息写入测试输出/公开截图/自动记忆。

## 11. 每次交付的固定收尾

AI 用简短说明和可打开证据回答：

1. 实际完成了什么，涉及哪些端和数据链路；未完成/未接通明确列出。
2. 测了什么、在哪里测、结果是什么；静态推断与实际复现分开。
3. 是否有新的迁移/配置/权限/部署步骤；哪些尚待授权。
4. 已知限制与剩余风险，下一步按优先级列出，不把报告当整改完成。
5. 复用规则或模块资料需要同步时只记稳定非敏感结论；不要把一次测试的状态写成永久事实。

交付包不是 Git 提交、push 或部署。没有请求不得执行这些动作；未运行的命令不得写成“通过”，曾经跑过不能冒充本次版本。

## 12. 如何复用到下一次对话/其他项目

本项目入口为[根 AGENTS.md](/Users/th/Desktop/Full愈-时叙/AGENTS.md)。它指向本规范、模板和审计台账，不自动修改线上配置或权限。支持自动读取 AGENTS 的工具可利用该入口；其他工具需手动附上文件路径。**本次没有安装全局插件，也没有让所有 AI 工具自动生效。**

其他项目：复制本规范和[模板](03-功能契约与验收模板.md)，先填真实工程/约束/业务差异，再把对应规范入口放入该项目支持的说明文件；不要照搬时叙路径、权限和经营参数。接入规则文件须遵循那个项目的授权流程。

可直接对 AI 说：

> 本次按项目 AGENTS.md 和《可复用AI开发方法论》执行。先自行检查管理配置、全部相关端、服务端授权、持久化、状态机、异常恢复和独立验收。只问会改变经营口径的问题，不让我逐项提醒工程完整性。不要重做既有设计，不接未授权真实系统。按证据分级交付，不用“页面可用/测试数量”代替业务完成。
