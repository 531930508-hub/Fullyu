# 功能契约、验收与交付模板

使用方式：AI 按任务大小填写必要部分。下列“待填”是可复制模板槽位，不是已经交付的功能；进入开发前，关键安全/经营规则不得仍为待定。无关项写“不适用＋原因”。不能让用户代填技术细节。

```text
功能编号/名称：
业务目的与使用角色：
本次范围 / 明确不做：
原有 UI/交互基线：
权威工程与相关模块：

经营规则：
- 正常结果、失败结果、禁止结果：
- 涉及的钱/数量/日期/归属口径：
- 哪些确需用户决策，AI 的推荐和影响：

多端影响：
- 总部配置/审核入口：
- 门店执行入口：
- 顾客端显示/操作：
- 后台任务/通知/对账：

接口：输入/输出/单位/枚举/错误码/分页：
授权：身份＋动作＋对象范围＋字段范围：
持久化：权威表、关系、唯一性、条件更新、历史快照：

状态机：允许与禁止的迁移：
并发与幂等：稳定业务键、相同键异内容、冲突结果：

独立验收规则（先定义，不能从实现倒推）：
```

## 模板 B：配置清单行

| 字段 | 必须填写的内容 |
|---|---|
| 业务名称/配置键 | 不是只写前端变量名 |
| 配置或常量 | 为什么可改/不可改；不是所有文案都必须 CMS |
| 所有者/范围 | 总部/区域/门店；是否允许覆盖 |
| 数据类型/单位 | 分、克、件、时区、日期、空值含义 |
| 默认/校验 | 默认来源，缺配置是否拒绝，边界/互斥 |
| 写入口/权限 | 页面＋API，谁能改什么字段 |
| 权威存储 | 表/字段、版本、约束 |
| 生效 | 即时或发布后、时间、旧单快照策略 |
| 消费者 | 小程序/门店/总部/任务各自在哪里使用 |
| 刷新与冲突 | 版本/缓存失效/并发编辑/旧数据提交 |
| 审计与撤销 | 谁改了什么、失败如何回退、历史不覆盖 |
| 验收 | 新值→保存→新请求→重启→实际规则生效 |

## 模板 C：持久化与敏感数据台账

| 数据 | 权威位置 | 账号/门店隔离 | 生命周期/TTL | 版本/迁移 | 恢复/清理 | 敏感性与展示权限 | 验收证据 |
|---|---|---|---|---|---|---|---|
| 经营事实（逐项填写） | 服务端 | 明确对象授权 | 业务/合规保留规则 | 迁移与约束 | 备份、冲正，不任意删除 | 最小必要字段 | 新请求/重启/恢复 |
| 执行任务（逐项填写） | 持久任务 | 业务对象范围 | 重试/过期/人工处理 | 稳定业务键 | 领取超时恢复 | 输出脱敏 | 各故障点中断 |
| 草稿（逐项填写） | 本地或服务端 | 环境＋账号＋门店 | 明确过期起算点 | 缓存版本/兼容 | 成功清理、失败保留 | 不缓存支付凭证 | 切店/换号/过期 |
| UI 状态（逐项填写） | 内存/本地 | 按需隔离 | 短期 | 按需 | 不影响经营事实 | 不推导身份/价格 | 刷新不损业务 |

## 模板 D：角色与对象权限矩阵

角色名和动作根据项目填写，以下是覆盖维度，不是给现有账号新增权限。

| 角色/范围 | 列表/详情 | 创建/修改 | 审批/执行 | 汇总/导出 | 可见字段 | 必须拒绝 |
|---|---|---|---|---|---|---|
| 顾客 A | 仅本人对象 | 本人允许字段 | 不适用则明确 | 本人必要记录 | 不含内部成本 | B 的对象、body 伪造身份 |
| 门店 A 操作者 | A 范围；跨店领取另定义最小例外 | 授权动作 | 有对应动作权才执行 | 不因导出放大全店 | 履约所需字段 | 店 B 写入、总部专属动作 |
| 总部/区域 | 显式授权集合 | 按管理职责 | 审批权限不等于款项已执行 | 对应范围 | 财务权限另控 | 越出组织范围 |
| 有角色但零门店 | 空/拒绝 | 拒绝 | 拒绝 | 空/拒绝 | 不得返回全量 | 空集合当全部 |
| 停用/撤销会话 | 拒绝 | 拒绝 | 拒绝 | 拒绝 | 不返回敏感信息 | 旧令牌继续使用 |

至少有直接 HTTP 用例验证每个“必须拒绝”。显示/隐藏菜单只能改善体验，不能作为证据。

## 模板 E：验收场景卡

```text

环境与版本：
前置状态与合成数据：

Given：
When（必要时给精确故障点/并发屏障）：
Then：
- 界面与API结果：
- 数据库/库存/资金不变量：
- 不应该发生的副作用：
独立校验方式：
执行命令/步骤：
实际结果：未执行 / 通过 / 失败 / 阻塞（附原因）

```

并发验收应使用可控屏障制造同读旧状态的交错，不靠随机 sleep 偶然碰撞；运行在目标数据库，重复执行并记录结果。故障测试优先在隔离环境做，不为“验证”向真实支付发款。


## 已填写示例：时叙退款审批（目标契约，不是当前已实现声明）

**目的**：操作者对可退商品发起退款，按总部规则决定直接执行或审批；任何页面都能区分“申请已提交”“批准”“渠道退款处理中”“已退款”“失败/待核对”。关联审计项 TX-04/05/12、UI-05。

**范围**：保留当前退款弹窗与审批列表结构，补齐状态、服务端报价和恢复。并不授权接真实支付或修改 schema；实现前单独确定相应变更。

**规则与数据**：

- 总部维护是否启用审批和金额门槛（单位分）；无直接退款权限者不能因关闭门槛而自动获得直接退款权，具体政策须明确。
- 服务端返回可退行、数量、金额、是否已制作、是否需审批及规则版本；前端不再复制固定 50 元判断。
- 提交形成稳定 refundRequestId，记录订单、行/履约单位、金额、理由、操作者、报价/规则版本和执行状态。
- 占用可退余额/数量与创建退款意图为原子动作；竞争失败返回冲突并重新报价，不先调渠道再发现超退。
- 决定与执行分开；同一意图重试使用同一渠道退款参考。渠道超时记未知并查结果，不能直接重建新退款。
- 未制作退款撤销对应杯的履约资格并按历史实际耗用冲回；已制作不冲回已消耗原料。部分已制作按单位事实，不用整单猜测。
- 前端按明确枚举展示，缺字段/未知枚举报可观察错误，不默认成功；渠道确认后财务流水与实际退款对齐。

**验收样例（本次均为待整改目标）**：

| ID | Given / When | 必须 Then |
|---|---|---|
| RF-A | 门槛20元，申请30元退款 | 返回申请已提交，资金未减少；不是“已退款” |
| RF-B | 已批准，渠道超时 | 决定=通过，执行=未知/待核对；可查询，不生成第二笔退款 |
| RF-C | 一行两杯，未制作退一杯 | 仅一杯可履约；一杯按历史用量回库；金额符合累计舍入 |
| RF-D | 两名操作者并发退同一剩余杯 | 只有一个意图成功占用数量；另一方冲突；不双退 |
| RF-E | 渠道成功后本地确认前中断 | 重启能用稳定ID查询并补记一次，无重复退款 |
| RF-F | 店A操作店B订单 | 服务端拒绝，无审批/退款/日志敏感数据泄露 |
| RF-G | 总部门槛改为100元，门店常驻旧页 | 以服务端新报价判断；界面说明同步或明确重新确认 |
| RF-H | 先售8g配方，后改10g再退旧单 | 按旧单实际耗用退回，不按现商品10g |

现有系统尚不满足上述全部条件；此表是后续实现验收基准，不可勾为已通过。

## 最后一分钟自检（AI 自己完成）

- 我是否把“有接口/有表/有按钮”当作闭环？
- 新店、新商品、新规则是否仍需开发改代码？如果是，是否有合理且明确的固定理由？
- 清内存、服务重启后，经营事实与待执行任务是否还能恢复？
- 换账号、零门店范围、伪造对象 ID 会不会扩权？
- 同一操作重试、两人同时做、外部已成功但响应丢失，会不会重复钱/货？
- 测试是否独立验证正确规则，还是仅顺着实现断言？
- 哪些结论只是静态判断或 mock，是否已经明说？
- 是否不小心更换 UI、读取凭证、写生产、改权限或发布了未授权内容？
