# Full愈 技术架构说明

> 品牌运营系统 · 微信小程序 + PC 管理后台 + NestJS 后端
> 本文档整理项目所用的技术栈、整体架构，以及架构的主流度 / 可扩展性 / 可维护性评估。

---

## 一、整体架构

- **形态**：pnpm workspace 管理的 Monorepo（单仓库多包）
- **包管理器**：pnpm 10.34.4
- **语言主基调**：TypeScript 全栈
- **目录结构**：
  - `apps/*` —— 三个应用：小程序（miniprogram）、管理后台（admin）、后端服务（server）
  - `packages/*` —— 共享包：`shared`（共享类型/逻辑）、`design-tokens`（设计变量）

```
Full愈/
├── apps/
│   ├── miniprogram/   # 微信小程序（uni-app + Vue 3）
│   ├── admin/         # PC 管理后台（Vue 3 + Vite）
│   └── server/        # 后端服务（NestJS）
├── packages/
│   ├── shared/        # 跨端共享类型与业务逻辑
│   └── design-tokens/ # 设计令牌（色彩/字体/间距）
├── .github/workflows/ # CI/CD（GitHub Actions）
└── docker-compose.yml # 本地/生产容器编排（含 PostgreSQL、Redis）
```

## 六、技术选型一句话总结

> 以 **TypeScript** 贯穿全栈，前端用 **Vue 3 生态**（小程序 uni-app + 后台 Vite），后端用 **NestJS + Prisma + PostgreSQL + Redis**，通过 **pnpm Monorepo** 统一管理、**Docker + GitHub Actions** 部署到**阿里云 ECS**。

## 七、架构评估

### 7.1 主流度：⭐⭐⭐⭐☆（很主流）

| 层面 | 选型 | 主流程度 |
|---|---|---|
| 语言 | 全栈 TypeScript | 当下最主流的全栈方案之一 |
| 前端框架 | Vue 3 | 主流三大框架之一，国内尤其流行 |
| 小程序 | uni-app | 国内跨端事实标准，社区大 |
| 后端 | NestJS | Node 后端最主流的企业级框架 |
| ORM | Prisma | TS 生态增长最快的 ORM 之一 |
| 数据库 | PostgreSQL | 业界最受推崇的开源关系库 |
| 缓存 | Redis | 缓存/锁的绝对主流 |
| 工程 | pnpm Monorepo + Docker + GitHub Actions | 现代标准工程实践 |

**评价**：无冷门/过气技术，也无过度实验性框架。招人、查资料、社区支持都容易，利于长期维护。

### 7.2 可扩展性：⭐⭐⭐⭐☆（业务扩展强，超大流量需演进）

**优势**
- 全栈 TS + Monorepo + `shared` 包：前后端共享类型，加功能改动可控、不易出错。
- NestJS 模块化：按业务模块（课程、订单、预约、候补…）组织，加新模块成本低。
- PostgreSQL：支持复杂查询、事务、JSON 等，业务复杂化不易撞墙。
- Redis 分布式锁 + 定时任务：为高并发场景（抢课、候补队列）打好基础。

**需注意的瓶颈**
- 单体后端：业务量不大时是优点（简单、好维护）；并发极高或团队变大时需考虑拆分或水平扩容。
- 定时任务 + 内存态：多实例部署时需确保定时任务只在一个实例执行（已具备 Redis 锁条件，需显式设计）。

### 7.3 可维护性：⭐⭐⭐⭐⭐（很好）

- 类型安全全覆盖：TS + Prisma 让"改数据库字段 → 编译期报错"，降低维护踩坑。
- 约定统一：Prettier、design-tokens、Monorepo 统一依赖，协作一致性高。
- NestJS 依赖注入 + 分层：Controller / Service / Module 职责清晰，新人易上手。
- 文档齐备：已有数据模型 / PRD 终版文档，利于长期维护。

## 八、务实改进建议（非必须，按需推进）

1. **可观测性**：尽早加结构化日志 + 错误监控（如 Sentry）和基础健康检查，上线后排障更轻松。
2. **数据库高可用**：数据库/Redis 目前在 ECS 上用 Docker 自建，起步可行，但要做好定时备份与磁盘监控；业务稳定后可平滑迁移到阿里云 RDS / 云 Redis（托管、自带备份与高可用）。
3. **测试**：对核心交易链路（下单、锁价、候补）补少量集成测试，回归最省心。
4. **部署演进**：当前 SSH 到 ECS 部署适合单机起步；未来需弹性伸缩时可考虑容器编排或阿里云容器服务。

---

## 九、总体结论

> 这是一套**选型正确、架构清晰、维护友好**的现代全栈方案，非常适合当前"品牌运营系统"的规模。
> 其路线是"**先做稳、易维护的单体，再按增长逐步演进**"——最务实、风险最低的技术路径，无明显误区。
