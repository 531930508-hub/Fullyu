**2026-11-23 决定：前端统一 Vue 3 + TS + Vite（后台 Ant Design Vue，小程序 uni-app），后端 NestJS + Prisma。**

原因：三个小程序已是 uni-app + Vue 3、在场后台已是 Vue 3，改造成本最小；一套语言覆盖小程序 + H5 + 后台 + 服务端。细则见 `docs/前端技术规范.md`。不要再讨论是否改用 React。

---

**2026-11-23 决定：时叙后台保持 React，不做框架迁移、不并入 CRM 平台。**

原因：约 13,300 行（AdminApp 7,483 / StoreApp 3,541）、26 个导航项、门店每天在用、页面级测试为零。与其它系统的衔接全部发生在服务端（`shixu/apps/server/src/crm/crm.client.ts` 调 CRM `/api/external/*`，HMAC 签名），前端框架对互通零影响。统一技术栈的收益小于门店回归风险。

重新评估的触发条件（满足任一才启动）：
1. 要做跨后台统一账号 / 单点登录；
2. 时叙后台要接入平台进销存（现在只有自己的 `Stock` 简版）；
3. 团队只剩 Vue 人手。

真要动时，第一步是 React 内部按导航项拆文件（框架不动），不是整体重写。

---

**2026-11-23 决定：CRM 后台按平台壳方案换壳，成为中后台平台（CRM 只是其中一个模块）。**

顺序：阶段 0 起 Vue 3 壳（登录/布局/菜单装配/权限指令/请求层）→ 阶段 1 迁 CRM 16 个页面（API 零改动）→ 阶段 2 补平台能力（权限表化、组织门店主数据、dataScope）→ 阶段 3 起搬进销存。旧零构建后台保留一个版本周期用于回滚。

---

**2026-11-24 决定：CRM 是会员卡唯一真源，轻疗本地权益表只做可查询投影；不做前台完整信息页。**

原因：顾客身份、卡期、退款状态和权益归属必须统一，避免轻疗与 CRM 各自计算出不同结论。轻疗以 `crm_card_id` 幂等回填与增量同步，进程首轮全量、之后每小时回看两天；同步失败不推进水位、不合成会员权益，失败只影响同步而不阻塞排班看板。畅练附赠卡停止新发，历史 `FY_BUNDLE` 数据保留兼容；赠卡与付费卡权益一致。

---

**2026-11-24 决定：会员卡同步与三端分享菜单先同步 `main` 并上传小程序开发版，生产留待当晚随其他需求统一上线。**

原因：用户明确要求暂不单独发布生产；直接推送含 `presence/**` 改动的 `main` 会触发在场生产自动部署，因此本次提交使用 `[skip ci]` 跳过自动部署，只做代码入库和小程序开发版上传。
