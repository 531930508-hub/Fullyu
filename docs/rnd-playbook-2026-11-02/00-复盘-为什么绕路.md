# 时叙 + 在场研发复盘：为什么绕路，下次怎么少绕

> 日期：2026-11-02。范围：时叙茶饮三端（小程序 / 管理后台 / 服务端）与 Full愈在场既有系统。  
> 性质：过程复盘与默认规范，不是发布授权，也不替代各项目自己的 AGENTS.md 和安全边界。  
> 事实来源：发布记录、审计报告、质量报告、现有代码与项目记忆；所有版本号和包体均来自当次上传/部署记录。

## 1. 先给结论

这次时叙从“能跑”走到“差不多可用”，真正花时间的不是写页面，而是四类返工：

1. **基线被当成灵感**：V7 Demo 只被当作风格参考，没有当成逐屏逐功能的验收合同，导致三端整体返工。
2. **默认项没有默认做**：分享、隐私登录、安全区、输入框、加购反馈、字体角色、订单生命周期，都要用户单独提醒后才补。
3. **外部契约靠试**：汇付的交易类型、成功码、退款必填字段、微信隐私声明，都是先写再撞，撞了再改。
4. **“做完”的证据太低**：页面能打开、编译通过、单测数量、上传开发版，经常被当成“功能完成”。

对应的五条原则是：**先定基线、默认项默认做、按闭环交付、证据分级、变更冻结**。具体清单见本目录其余文档。

## 4. 时叙时间线里最值得记住的几件事

### 4.1 视觉：四版顶部，两版字体

- 1.0.5 顶部下移；1.0.6 按在场比例做 150rpx + 左 10%，用户反馈“logo 还是太小，放在左边”；1.0.7 改 120×22 贴左；1.0.8 才把 logo 与语言切换的中线对齐。
- 根因不是审美，是**没有把在场已认可的几何关系当成输入**，以及**用 H5 的内联 px 与 CSS px 混算**。
- 1.0.16 才建立三字族；1.0.17 才把字距统一为 0.05/0.06/0.12/0.18em。此前 9.5/10.5/11.5/12.5/17/19/22/23/25 等零散字号并存。

### 4.2 支付：三次“以为对了”

- `00000100 下单成功` 被通用失败分支判为失败 → 预下单明明成功，前端却报错。
- `T_NATIVE` 一直报 `23000004 交易类型不支持`，不是参数错，是产品/子商户未开通；继续改字符串没有意义。
- 退款缺少 `org_req_date`，汇付明确拒绝 `10000000`，但被当成“结果未知”，于是 `pendingRefundQty` 一直占用，A013 退不了。
- 最后靠“真实小额 + 假付款码 + 退款重试 + DB/流水核对”才收口。**支付不是页面功能，是契约、状态机和对账。**

### 4.3 隐私与分享：一半在代码，一半在公众平台

- 手机号一键登录不弹原生面板，根因是《用户隐私保护指引》没有声明手机号；页面勾选框补不了。
- 保存海报到相册失败，根因是没声明“相册（仅写入）”；`scanCode` 不需要声明摄像头，过度声明会被驳回。
- 分享必须每页注册两个回调；朋友圈 `query` 置空，避免把订单号/券码带出去；小程序码只能服务端 `getwxacodeunlimit`。
- 这些都属于“代码 + 控制台配置 + 真机”三件事，缺一件就不算完成。

### 4.4 部署：三个“看起来正常”

- 构建成功但 API 指向 localhost。
- 校验文件返回 200，但内容是 SPA 的 `index.html`。
- 旧 admin 标签页打旧 bundle，服务端已修但页面仍报旧错。
- 结论：**状态码、构建成功、页面能开，都不是部署证据。**

## 5. 在场经验：哪些直接复用，哪些不能照搬

在场是 Java Spring Boot + MyBatis Plus + MySQL 服务端、Vue 2 + Element UI 后台、uni-app 小程序。它的研发约束和时叙不同：本机可能没有 JDK/Maven，很多改动只能交给开发团队编译；共用库里存在其他系统的表；后台与小程序经常要跨仓库同步。由此得到三条经验：

- **验证边界要诚实**：没有编译就写“未编译”，静态检查不等于运行通过；交付包要写清待开发团队完成的编译、联调、绑定真实 ID。
- **数据库不是本项目独有**：schema 漂移是常态，未知表只增不删；发布前全库备份，不能按 migrate diff 清理。
- **设计与代码都可能过期**：旧设计文档的配色/组件不自动等于当前品牌标准；使用前核对权威源和版本，不把历史方案当已批准规范。

### 可以直接复用

- **布局几何**：顶部状态栏/胶囊、底部安全区、选店/登录/搜索框的成熟实现。时叙顶部被退回时，直接按 `full-yu-mini2` 的坐标系来。
- **分享收口**：`utils/appShare.js` 统一注册两个分享回调；个人中心分享弹层；邀请海报与 `createWxaCodeUnlimit`。
- **财务模型**：独立 append-only 台账、月度 OPEN/CLOSED、历史月冲减不修改、`dedupeKey` 唯一、快照字段。
- **权限模型**：GROUP/DEPT 数据范围、`scope.toWhere`、总部外采/门店领用的职责分离、4256 约束、供货价强制。
- **设计标准**：作为结构参考（色彩角色、组件、交互模式），但使用前必须核对版本。

### 不能照搬

- 不能把在场旧设计文档里的六色当成当前品牌标准：用户已明确对旧色系不满意，新 VI 未批准前不能迁移。
- 不能把在场 Java 的编译/测试假设搬到本机：没有 JDK/Maven 就写“未编译”。
- 不能按 migrate diff 清理未知表：共用库里有会员同步、支付流水等其他系统的表。
- 不能因为“参考了在场”就修改在场代码；只读参考，改动需单独授权。

## 6. 五条工作原则

### 原则一：先定基线，再动手

基线可以是 V7 Demo、在场页面、已批准设计稿或现有生产页面。基线不是“感觉像”，而是**逐屏、逐状态、逐功能的对照表**。有基线时，先原样引入其样式层，再做适配；不要一边看一边自写一套。

### 原则二：默认项默认做

分享、隐私、安全区、空/错/载、加购反馈、字体角色、订单生命周期、权限负向、持久化、审计，这些不是“加需求”，是**产品能上线的最低配置**。每项要么完成，要么在交付表里写“不适用 + 原因”，不能沉默省略。

### 原则三：按闭环交付，不按页面交付

一个功能至少回答：谁配置 → 谁使用 → 服务端怎么授权/校验 → 数据存哪 → 再进入怎么读回 → 失败怎么恢复 → 怎么独立证明。页面只是入口，不是交付单位。

### 原则四：证据分级，不混成一个“完成”

- E0：只有方案/静态原型。
- E1：源码存在，静态检查/类型/构建证据。
- E2：隔离环境真实 DB + API/跨端业务闭环，外部可 mock。
- E3：目标部署形态下故障、并发、安全、恢复验证。
- E4：经授权的真实集成/真机/试点验收。

写“通过”时必须带级别、日期、命令、环境、未测项。mock 通过不等于真实通道通过；开发者工具不等于真机；上传开发版不等于体验版/审核/发布。

### 原则五：变更冻结与可回滚

视觉基线、设计 token、接口契约、数据库 schema、发布版本，一旦确认就冻结。要改，先说明影响面、迁移/回滚方式，再动。没有冻结，就会在同一处反复返工。

## 7. 下次的量化目标

| 指标 | 这次 | 下次目标 |
|---|---|---|
| 视觉首次对齐返工 | 顶部 4 版、字体 2 版 | 同一区域 ≤2 版；第 2 版必须附基线对照截图 |
| 支付 live 前矩阵 | 边联调边发现 | 契约表 + 矩阵 100% 有证据，再切 live |
| 默认能力漏项 | 分享、隐私、安全区、反馈均被提醒 | 清单 0 漏项；不适用项写明原因 |
| 每次交付证据 | 有时只有“构建通过” | 每次 1 张证据表（E 级别/命令/环境/未测） |
| 三端发布一致性 | H5 曾落后小程序两版 | 发布表逐端写版本；未部署显式标旧 |
| 版本节奏 | 几天内 17 个开发版 | 一个功能批次 ≤3 个开发版，除真机阻塞外不反复 |
