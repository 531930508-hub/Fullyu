# 发布与分支规范（Full愈 全仓库）

> 适用：`presence/`、`shixu/`、`crm/`、`qingliao/**` 的任何改动从本地到线上的全过程。
> 本文是**跨项目总则**；项目细则：在场 `docs/deploy/发布标准流程.md`、时叙 `shixu/AGENTS.md`、轻疗 `qingliao/docs/`。冲突从严。
> 域名/机器/端口唯一事实源：`docs/deploy/domains.tsv`。凭据：`~/.fullyu-secrets/`（不进仓库）。

## 0. 一句话

**`main` 是唯一可发布分支；发布单位是 `(项目, commit)`；每次生产发布打 `prod-*` tag；服务器只接收产物，不接收手改。**
**分支不合并 = 下一次从 `main` 发布就把它覆盖**（§8：时效、覆盖防护、线上 commit 回读）。

## 1. 为什么不是"每个系统一条分支"

分支隔离的是**整棵树的快照**，不是目录。切到"时叙分支"时，在场/CRM/轻疗的目录会一起变——你要的"同时开两个系统"反而变成整仓来回切、未提交改动跟着跑。真正的隔离靠三样，且已经在生效：

| 机制 | 现状 |
|---|---|
| commit 按路径划分 | `git add presence/...` 与 `git add crm/...` 是两个独立提交 |
| CI 按 `paths` 过滤 | 改时叙不会触发在场构建：`.github/workflows/ci-deploy.yml` 只看 `presence/**` |
| 部署按目录打包 | 每个项目只打包自己的产物，互不携带 |

所以"同时改四个系统"= 四个提交，发布时各发各的 `(项目, commit)`，互不等待。需要物理隔离（各开一个目录、各跑 dev server）时用 **worktree**，不用分支：

```bash
git worktree add ../wt-shixu main
git worktree add ../wt-presence main
```

## 3. 三道门

### G0 · 本地门（每次发布前必过）

```bash
scripts/release-check.sh --project presence   # 或 shixu / crm / qingliao-mini / all
scripts/release-check.sh --project presence --full   # 额外跑单测
```

判据：分支名合规、工作区内**本项目目录**干净、与 `origin/main` 不落后、构建全绿。红了就停，不许"先合了再修"。

### G1 · Git 门

```bash
git switch main && git pull --ff-only
git merge --ff-only <分支>            # 有冲突就停下来问，不要强推
git push origin main                  # remote 为 SSH；HTTPS 无凭据
git rev-list --count origin/main..main   # 必须输出 0
git log --oneline -1 origin/main         # 必须是你刚推的 commit
```

判据：`origin/main` 确实含该 commit；在场还要看 CI `build-check` 绿、`deploy` 是否出现（不出现 = `ENABLE_DEPLOY` 未开）。

**推功能分支永远不会上线**，别把"推上去了"说成"发布了"。

### G2 · 服务器门

按 §2 矩阵走对应通道，然后：

1. 跑该项目的**最小探针**（§4），记录前后值；
2. `scripts/release-tag.sh <project> "一句话说明"` 记账（§5）；
3. 按 `AGENTS.md` §6 的格式汇报。

## 4. 探针

```bash
curl -s -o /dev/null -w 'presence %{http_code}\n' https://presence.fullyu.cn/api/v1/health
curl -s -o /dev/null -w 'teahour  %{http_code}\n' https://teahour.fullyu.cn/api/health
curl -s -o /dev/null -w 'crm      %{http_code}\n' https://crm.fullyu.cn/api/health
curl -s -o /dev/null -w 'mall     %{http_code}\n' https://cityretreat.fullyu.cn/
```

- 新接口要**发布前 404 → 发布后非 404**，否则不能证明新版生效。
- 本机代理会缓存甚至伪造 502；静态产物以 ECS 上 `md5sum` 与本地构建产物比对为准，不要用本机 curl 的 HTML 判断。
- 后台目录被整体替换过时，bind mount 的容器会绑在旧 inode 上——宿主机 md5 正常但用户看不到新版，需 `docker restart`。细节见 `docs/deploy/发布标准流程.md` §3.5。

## 5. 版本记账：只用 tag，不维护表格

```bash
scripts/release-tag.sh presence "课程页头两行布局"   # 在 main 上、干净、已同步时才能打
scripts/release-tag.sh presence "..." --push        # 同时推到远端
scripts/release-status.sh                            # 看各项目当前线上版本
```

- 命名：`prod-<project>-<yyyymmdd-HHmm>`，`project ∈ presence|shixu|crm|qingliao-mini|qingliao-mall`；测试环境用 `test-<project>-...`。
- 前后端**分开发布**的项目用变体：`prod-qingliao-mall-web-<yyyymmdd-HHmm>`（管理端 dist）、`prod-qingliao-mall-api-<...>`（jar）。2026-11-21 补记 11-20/21 四次部署时确立（当时 02:50 的 dist 与 23:52 的 jar 是两次独立部署，一个 tag 记不下）。`scripts/release-status.sh` 按变体分行显示，`scripts/pending-release.sh` 按变体核对；`scripts/release-tag.sh` 目前只生成基础家族，分变体需手工 `git tag -a <tag> <commit>`。
- **按 tag 名字里的时间排序**，不看创建时间：补记旧 tag 不会因为"刚创建"排到最前面。
- annotated tag，message 三行：commit、探针结果、回滚点。
- 表格会漂移，tag 不会：`git tag` 就是线上版本账本，任何人 clone 后可查。

## 6. 服务器红线

允许与仓库不同的**只有**：`.env*`、`node_modules`、上传/备份目录。其他任何差异按事故处理。

- ECS 上不是 git 仓库，部署靠源码包/产物覆盖；**不要在服务器上 `git pull`**。
- 在场后端有两套目录：pm2 跑 `/root/fullyu`（新），systemd `fullyu-api.service` 跑 `/opt/fullyu`（旧）。3000 端口只能有一个主。部署后必须 `ss -lntp | grep :3000` 核对归属；prisma client 必须从 `/root/fullyu/node_modules` 加载。
- 数据库只用 `prisma db push`；**禁止** `migrate dev` / `migrate reset`。`db push` 失败被吞 = 运行期 500，部署脚本的 `migrate diff` 兜底不可绕过。
- 覆盖静态目录一律 `rsync -az dist/ host:web/`，**不加 `--delete`**（目录里有微信验证文件、独立落地页、预置 `assets/`）。
- 备份用脚本，不用 `cp -a`：

```bash
deploy/scripts/backup-dist.sh /opt/fullyu/apps/admin                  # dist.bak-*，保留最新 2 份
deploy/scripts/backup-dist.sh --prefix h5.bak- /opt/fullyu/apps/miniprogram/dist/build
deploy/scripts/prune-backups.sh --dry-run /opt/fullyu/apps/admin      # 先看再删
```

## 8. 合并时效与覆盖防护

**模型**：发布只认 `main`，分支只是运输工具。分支上的提交没合回 `main`，下一次从 `main` 构建发布就会把它"覆盖"——不是谁手滑，而是它从来不在发布源里。已经发生过两次：11-20 13:53/14:25 两次生产 dist 回退了"一键拨号"和"总助可见手机号"（`qingliao/docs/ops/生产上线手册.md` 866、901 行），11-21 02:41 测试环境一次发布被随后从 `main` 构建的产物覆盖（取证方法见 commit `8af8256`）。

### 8.1 时效

| 规则 | 判据 | 超了怎么办 |
|---|---|---|
| 短期分支 **≤ 48 小时**合回 `main` | 最老未合提交的年龄 | 近期不发的改成 `parked/<scope>-<日期>` 并写复查日期（§7） |
| **合并 ≠ 上线** | 合入后有没有打 `prod-*` tag | 还不该生效的，以"未启用/开关关闭"状态合进 `main`，不要靠"留在分支上等等再发" |
| **一个任务一个 worktree** | `git worktree list` | 多会话在同一目录切分支，会把别人的提交带跑、甚至把自己的提交丢在旧分支上（`/AGENTS.md` §5 分支纪律、§6 并行会话纪律） |

### 8.2 发布前两条核对（在 G0 之前，30 秒）

```bash
scripts/pending-release.sh             # 未合 main 的提交 + 线上当前 commit
scripts/pending-release.sh --strict    # 有风险时退出码 1，可挂进发布脚本
```

判据：

1. **未合 `main` 的提交**里，凡触达可发布目录（🔥）的必须当场决定：合 `main`，或明确记为废弃；
2. **线上 commit 必须 ∈ `main`**。不在 `main`，说明线上跑的是某条分支或旧提交构建的产物，下一次从 `main` 发布必然覆盖它。

脚本不可用时的手工等价核对：

```bash
git log --oneline origin/main..<分支>     # 我有东西没合
git log --oneline <分支>..origin/main     # 别人合了、我这条分支没带上
git branch -a --contains <线上commit>     # 线上那个 commit 到底在哪条分支上
```

### 8.3 判定与动作

| 现象 | 判定 | 动作 |
|---|---|---|
| 线上 commit 不在 `main` | 🔴 覆盖风险（下一次发布即回退） | 先把那条分支合进 `main`（`--ff-only`），再按 §3 的 G1/G2 重发；**不要**拿别的分支产物去"补" |
| 线上 commit 在 `main`，但与最近 `prod-*` tag 不一致 | 🟡 记账滞后 | 补 tag（`scripts/release-tag.sh`），并说明这次是谁发的、为什么没记。轻疗商城前端/后端分开发布但共用一个 tag 家族（`qingliao-mall`），一个 tag 只能记一个 commit，以"是否在 main"为准 |
| 分支最老未合提交 > 48 小时且触达可发布目录 | ⏰ 迟早被覆盖 | 合 `main` 或转 `parked/`，不许"攒着下次一起发" |
| 分支提交的**内容**其实已在 `main`（sha 不同，cherry-pick/rebase 造成） | 不算未合 | 脚本用 `git cherry` 按 patch 等价性判，不会误报；`git rev-list`/`ahead` 数字会误报 |

### 8.4 线上 commit 怎么读（只读）

| 发布单元 | 回读方式 | 备注 |
|---|---|---|
| 轻疗商城前端 | `curl https://cityretreat.fullyu.cn/static/build-info.json` | 产物自带 `commit`/`builtAt`，由 `qingliao/tou-mall-admin-web/scripts/release-dist.mjs` 写入；测试环境同路径 `test-cityretreat.fullyu.cn` |
| 轻疗商城后端 | 120.55 上读活动 jar 的 `META-INF/MANIFEST.MF` → `Implementation-Build` | 构建必须传 `-Dbuild.commit`（`deploy-test.sh` 已做）；120.55 无 `unzip`，脚本用 `python3 zipfile` 读 |
| 在场 / 时叙 / CRM | 只能读产物 mtime | 产物没有 commit 标记，判不出 commit，属已知缺口（§10） |
| 小程序 | 微信后台版本号 | 人工核对 |

`scripts/pending-release.sh` 的只读边界：`git` 读、`curl` 只发 GET、`ssh` 只在服务器上跑 `ls/date/ps/python3` 读文件；不上传、不重启、不写服务器、不碰工作区里的未提交改动。

## 9. 事故处置顺序

1. **止损**：回滚产物（`/tmp/*.bak-*.tar.gz` 或上一版 dist/jar），不要先查原因；
2. **确认恢复**：跑探针，记录值；
3. **定位**：日志 → `git log` 二分 → 本地复现；
4. **修复**：走正常 G0–G2，不在服务器上改代码救火（`.env` 除外）；
5. **复盘**：写进本文或对应项目文档，别只留在对话里。
