```

                    │  teahour.fullyu.cn  → 121.40(主) / 120.55(备)                     │
                    │  cityretreat / crm  → 见下表                                       │

   ├ 在场    备             ├ 在场    主                      ├ 克隆测试库
   ├ 轻疗    备             ├ 时叙    备                      └ 构建机（保留 Jenkins/打包）

                    ┌──────────────── 云数据（杭州）────────────────┐
                    │ RDS 分库：qingliao_prod / fullyu_prod / teahour / crm │
                    │ 云 Redis 标准版主从（三品牌共用，分 db）              │
                    │ OSS：上传、备份、静态                                  │
                    └──────────────────────────────────────────────────┘
   47.111（1.6G）：腾空后释放；云 Redis 上线即摘掉它的 Redis，MQ 随轻疗迁移一起换
```

**每个服务在两台机器上都跑一份**，同一端口；主备靠 DNS 指向区分。数据层共享 → 备机是"温备"，切换即用。

### 2.1 为什么不用 ALB

ALB 能秒级切换，但按量计费 + 增加一层要给钱的组件；我们的切换窗口实际由**门店侧兜底**决定（PWA 离线队列 + 手写纸单），1–3 分钟切换对营业无实质影响。做法：

1. 两台机器都装健康检查脚本（每 30s 探测本地 nginx/进程/DB 连接，连续 3 次失败触发）
2. 失败时调阿里云 DNS API 把对应域名的 A 记录切到另一台（TTL 60s）
3. 必须**先在窗口内人工演练一次切换**（含切回），再改为自动

**代价（如实记）**：小程序/webview 可能缓存 DNS 更久，最坏 3–5 分钟；期间门店只能靠离线队列。若以后要求秒级，再回头买 ALB 或加一台极小反代机——现在不买。

### 2.2 云数据（2026-11-11 判断）

| 项 | 判断 | 理由 |
|---|---|---|
| RDS | **不新建实例，先分库**：`qingliao_prod` / `fullyu_prod` / `teahour` / `crm`，字符集一律 utf8mb4（现例默认 utf8mb3） | 已在杭州、延迟 1.5–4.6ms；拆实例只增加成本与运维，没有收益。**已确认（2026-11-13）**：**基础版（Basic）**，mysql.n2e.medium.1、MySQL 8.0、100G、包年至 2027-05-29。基础版无备节点，主库故障即停服；升高可用版是**新建实例 + DTS 迁移**，属窗口作业 |
| 云 Redis | **立刻上**标准版主从最小规格（1G），三品牌共用分 db | 替掉 47.111 无密码裸奔 Redis 与 8.133 本地 Redis；这是当前最脏的一处 |
| 消息队列 | **不单独上云**，跟轻疗迁移一起换（只有轻疗用 RabbitMQ） | 避免同时维护两套 MQ |
| OSS | 上传与备份统一走 OSS（已有 AK） | 时叙上传目录必须可被两台机器共享 |

### 7.2 schema 变更检查单（每次动表必走，顺序不能换）

1. **先备份整表**：`CREATE TABLE xxx_bak<日期> AS SELECT * FROM xxx;`
2. 手写 `prisma/additive-<feature>.sql`，**只加不删**，先在 RDS 执行
3. 同批改 `schema.prisma` 并 `prisma generate`
4. **再发代码**（列先于代码存在 = 新旧代码都能跑 = 零停机）
5. CI 的 `db push` 只负责对齐；跑之前确认没有未合并的手工 SQL
6. 回滚 = 回代码，**不删列**（留列不影响旧代码）

> 为什么强调顺序：CI 每次部署都会执行 `prisma db push`。如果只改了库没改 `schema.prisma`，下次 CI 会尝试把库"推回"旧结构；反之只改 `schema.prisma` 没执行 SQL，部署当场就会因为缺列报错。

### 7.3 案例：候补退款无限重试（2026-11-12 已根治）

**时间线**（证据取自 `pm2 logs fullyu-api`）
- 11-10 起：4 笔测试订单的候补退款每 5 分钟重试一次，流水号 `RF<orderId>` 冲突后追加 `_2/_3…`，最多到 `_583`，累计 **2332 条** `order_refunds`
- 23:30 仍在刷：`候补退款失败 cmvt…: 订单缺少汇付交易流水，无法退款`（bizCode **5105**，属**永久失败**，重试一万次也不会成功）
- 00:15 修复上线后：新进程（pid 199435）**零 ERROR**

**根因**：`refundFull` 遇到网关明确拒绝时会把订单从 `REFUNDING` 回滚成 `PAID` 再抛错；任务只 `logger.error`，条目留在 `WAITING` → 下一轮原样重来，无计数、无退避、无上限。

**四道闸**（`waitlist-tasks.service.ts`）
1. 失败计数 + 指数退避 5/15/60/360/1440 分钟（`refund_attempts` / `refund_next_retry_at`）
2. 5105/5106 明确拒绝 → 一次即停，标 `[需人工]`
3. 连续 6 次失败 → 停，标 `[需人工]`
4. 订单 `REFUNDING` → 交给对账任务，绝不重复发起；订单已 `REFUNDED` → 只补记条目终态

**另补三道**
- `payment.refundFull` 前置检查：已有 `PROCESSING/UNKNOWN` 流水直接跳过（防任何调用方重复退款）
- `refund-reconcile`：对账**封顶 12 次（≈1 小时）**，到顶停止自动查询并每小时打一条 ERROR（`[需人工]`），避免"查不到→刷新 updatedAt→下轮再查"的新无限循环
- 强制退款审批：不填金额时按**剩余可退金额**路由（原来按 `0` 匹配流程，可能命中最低档、甚至无规则直接放行大额退款）；同时校验退款金额不得超过可退金额
- 结课订单补全：扫描条件补上「今天及以前结课」，避免按 `createdAt` 取 500 条时，在售订单超过 500 后后面的订单永远扫不到、自退窗口失效

**验证**：`test/waitlist-refund-retry.spec.ts` 6/6；线上两轮定时任务无报错；新列 ORM 读写实测正常；最坏情况从 583 条/单降到 1–2 条/单。

**踩过的坑（下次别再踩）**
- `mysql` 选项文件里 `#` 是注释符：`password=jhSd3#623…` 会被截成 `jhSd3` → 表现为 `Access denied`，误以为白名单没开。**密码必须用双引号包起来**

**和 RDS 自动备份的关系**：RDS 备份扛"整实例/时间点"，dump 扛"能带走、能异地、能挑单库"；两者互补，不必二选一。建议 dump 保留最近 7 份（每份 11 MB，121.40 现余 26 G）。

### 7.11 维护页与"换 jar 不白屏"（P0-3，2026-11-13 已在生产验证）

**三个层次，按需用，别混着理解**

| 场景 | 触发方式 | 用户看到 |
|---|---|---|
| **换 jar / 重启进程**（最常见） | 不用做任何事：进程一停，nginx 拿到 502 自动兜底 | 页面：维护页（503 + 文案，30 秒自动刷新）；API：`{"code":503,"message":"系统维护中…"}` |

- 页面：`/server/www/mall-maint/__maintenance.html`、`__maint_api.json`

### 8.5 后台"白屏、刷新第二次就好"的成因与修复（2026-11-12）

现象：部分地址打开后长时间纯白，手动刷新一次立刻正常。

实测排除服务端慢：官网 `fullyu.cn` 首字节 166–215ms、整页 gzip 46KB；后端 `cityretreat` TTFB 150–250ms。

真正两个原因都在**后台前端**：

1. **渲染阻塞资源被墙**：`tou-mall-admin-web/index.html` 里
   `<link rel=stylesheet href="https://fonts.googleapis.com/css?family=Noto+Sans+SC...">`
   是阻塞渲染的样式表，而 fonts.googleapis.com 在国内连不通，浏览器要等 TCP 超时（Chrome 约 20–30s）才放弃渲染 → 整页白屏。
   第二次刷新时浏览器已记录该连接失败 / DNS 负缓存，快速失败，所以立刻出内容。**这是"刷新第二次就好"的直接成因。**
2. **后台 JS/CSS 未压缩**：8.133 的 `nginx.conf` 把 `gzip_types` 整行注释掉了，只有 `text/html` 被压缩。
   首屏裸传 3,127,430 B（vendor 1.94MB + tinymce 0.83MB + css 0.35MB + app 0.17MB）。
   弱网下就是 5–15s 白屏；第二次刷新命中缓存所以变快。

已修（两台机器均已 reload，无需发版）：

| 项 | 改动 | 效果 |
|---|---|---|
| gzip | 8.133 `nginx.conf` 打开 `gzip_types`(js/css/xml/json/svg) + `gzip_vary` + `comp_level 5` | 首屏 **3.13MB → 995KB** |
| Google Fonts | 仓库 `index.html` 与部署版 `/server/www/fully/dist/index.html` 均改为 `rel=preload + onload` 非阻塞 | 不再阻塞渲染 |
| 缓存策略 | `cityretreat.conf`：`/static/` 一年强缓存、`/index.html` no-cache（含 SPA fallback） | 二次访问直接命中；发版不取旧壳 |
| HSTS | `cityretreat.conf` 补 `Strict-Transport-Security` | 主域此前漏配 |

**踩坑记录（重要）**：`root` 必须写在 `server` 级。先前只写在 `location /` 内，新增 `location ^~ /static/`、`location = /index.html` 不继承 root，
导致 JS/CSS 404、首页回落到 `/usr/share/nginx/html` 的 nginx 默认欢迎页。今日两次踩到，整份 `cityretreat.conf` 已重写到 server 级 root。
以后给任何 vhost 新增 location 前，先确认 root/alias 的作用域。

环境备注：开发机 shell 带 `https_proxy`，`curl --resolve` 会被代理忽略（响应头出现 `200 Connection established`），
本机做"绕过 DNS 指向某台机器"的验证必须加 `--noproxy '*'`，否则测的是代理解析后的地址。

### 8.6 关闭 fullyu.cn 的微信短链 302（2026-11-12）
