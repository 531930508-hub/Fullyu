## 2. 目标拓扑（两台生产 + 一台测试）

```
                    ┌──────────────── DNS（TTL 60s，双 A + 健康探测切换）────────────────┐
                    │  presence.fullyu.cn → 120.55(主) / 121.40(备)                     │
                    │  teahour.fullyu.cn  → 121.40(主) / 120.55(备)                     │
                    │  cityretreat / crm  → 见下表                                       │
                    └──────────────────────────────────────────────────────────────────┘
   A 机 121.40（99G）        B 机 120.55（40G→扩 100G）       测试机 8.133（青岛，99G，轻疗搬走后启用）
   ├ 时叙    主             ├ 轻疗    主                      ├ 全部 test-* 环境
   ├ 在场    备             ├ 在场    主                      ├ 克隆测试库
   ├ 轻疗    备             ├ 时叙    备                      └ 构建机（保留 Jenkins/打包）
   └ CRM     主             └ CRM     备
                    ┌──────────────── 云数据（杭州）────────────────┐
                    │ RDS 分库：qingliao_prod / fullyu_prod / teahour / crm │
                    │ 云 Redis 标准版主从（三品牌共用，分 db）              │
                    │ OSS：上传、备份、静态                                  │
                    └──────────────────────────────────────────────────┘
   47.111（1.6G）：腾空后释放；云 Redis 上线即摘掉它的 Redis，MQ 随轻疗迁移一起换
```

**每个服务在两台机器上都跑一份**，同一端口；主备靠 DNS 指向区分。数据层共享 → 备机是"温备"，切换即用。

### 2.1 为什么不用 ALB

ALB 能秒级切换，但按量计费 + 增加一层要给钱的组件；我们的切换窗口实际由**门店侧兜底**决定（PWA 离线队列 + 手写纸单），1–3 分钟切换对营业无实质影响。做法：

1. 两台机器都装健康检查脚本（每 30s 探测本地 nginx/进程/DB 连接，连续 3 次失败触发）
2. 失败时调阿里云 DNS API 把对应域名的 A 记录切到另一台（TTL 60s）
3. 必须**先在窗口内人工演练一次切换**（含切回），再改为自动

**代价（如实记）**：小程序/webview 可能缓存 DNS 更久，最坏 3–5 分钟；期间门店只能靠离线队列。若以后要求秒级，再回头买 ALB 或加一台极小反代机——现在不买。

### 2.2 云数据（2026-11-11 判断）

| 项 | 判断 | 理由 |
|---|---|---|
| RDS | **不新建实例，先分库**：`qingliao_prod` / `fullyu_prod` / `teahour` / `crm`，字符集一律 utf8mb4（现例默认 utf8mb3） | 已在杭州、延迟 1.5–4.6ms；拆实例只增加成本与运维，没有收益。**待确认**：该实例是高可用版还是基础版——基础版需升级（你做） |
| 云 Redis | **立刻上**标准版主从最小规格（1G），三品牌共用分 db | 替掉 47.111 无密码裸奔 Redis 与 8.133 本地 Redis；这是当前最脏的一处 |
| 消息队列 | **不单独上云**，跟轻疗迁移一起换（只有轻疗用 RabbitMQ） | 避免同时维护两套 MQ |
| OSS | 上传与备份统一走 OSS（已有 AK） | 时叙上传目录必须可被两台机器共享 |

### 7.2 schema 变更检查单（每次动表必走，顺序不能换）

1. **先备份整表**：`CREATE TABLE xxx_bak<日期> AS SELECT * FROM xxx;`
2. 手写 `prisma/additive-<feature>.sql`，**只加不删**，先在 RDS 执行
3. 同批改 `schema.prisma` 并 `prisma generate`
4. **再发代码**（列先于代码存在 = 新旧代码都能跑 = 零停机）
5. CI 的 `db push` 只负责对齐；跑之前确认没有未合并的手工 SQL
6. 回滚 = 回代码，**不删列**（留列不影响旧代码）

> 为什么强调顺序：CI 每次部署都会执行 `prisma db push`。如果只改了库没改 `schema.prisma`，下次 CI 会尝试把库"推回"旧结构；反之只改 `schema.prisma` 没执行 SQL，部署当场就会因为缺列报错。

### 7.3 案例：候补退款无限重试（2026-11-12 已根治）

**时间线**（证据取自 `pm2 logs fullyu-api`）
- 11-10 起：4 笔测试订单的候补退款每 5 分钟重试一次，流水号 `RF<orderId>` 冲突后追加 `_2/_3…`，最多到 `_583`，累计 **2332 条** `order_refunds`
- 23:30 仍在刷：`候补退款失败 cmvt…: 订单缺少汇付交易流水，无法退款`（bizCode **5105**，属**永久失败**，重试一万次也不会成功）
- 00:15 修复上线后：新进程（pid 199435）**零 ERROR**

**根因**：`refundFull` 遇到网关明确拒绝时会把订单从 `REFUNDING` 回滚成 `PAID` 再抛错；任务只 `logger.error`，条目留在 `WAITING` → 下一轮原样重来，无计数、无退避、无上限。

**四道闸**（`waitlist-tasks.service.ts`）
1. 失败计数 + 指数退避 5/15/60/360/1440 分钟（`refund_attempts` / `refund_next_retry_at`）
2. 5105/5106 明确拒绝 → 一次即停，标 `[需人工]`
3. 连续 6 次失败 → 停，标 `[需人工]`
4. 订单 `REFUNDING` → 交给对账任务，绝不重复发起；订单已 `REFUNDED` → 只补记条目终态

**另补三道**
- `payment.refundFull` 前置检查：已有 `PROCESSING/UNKNOWN` 流水直接跳过（防任何调用方重复退款）
- `refund-reconcile`：对账**封顶 12 次（≈1 小时）**，到顶停止自动查询并每小时打一条 ERROR（`[需人工]`），避免"查不到→刷新 updatedAt→下轮再查"的新无限循环
- 强制退款审批：不填金额时按**剩余可退金额**路由（原来按 `0` 匹配流程，可能命中最低档、甚至无规则直接放行大额退款）；同时校验退款金额不得超过可退金额
- 结课订单补全：扫描条件补上「今天及以前结课」，避免按 `createdAt` 取 500 条时，在售订单超过 500 后后面的订单永远扫不到、自退窗口失效

**验证**：`test/waitlist-refund-retry.spec.ts` 6/6；线上两轮定时任务无报错；新列 ORM 读写实测正常；最坏情况从 583 条/单降到 1–2 条/单。
