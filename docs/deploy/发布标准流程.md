# 发布标准流程（Full愈 · presence）

> 适用：`presence/**` 的代码变更上线。域名/机器/端口事实源见 `docs/deploy/domains.tsv` 与 `docs/deploy/生产方案-最终版.md`；凭据见 `~/.fullyu-secrets/SERVERS.md`（不进仓库）。
> **本文只是在场细则**：分支模型、各项目通道矩阵、三道门、tag 记账见 `docs/deploy/发布与分支规范.md`；协作红线见根目录 `AGENTS.md`。

## 0. 一句话

**推 `main` → GitHub Actions 自动构建并部署到 ECS**，但需要仓库变量 `ENABLE_DEPLOY=true` 才真正执行 deploy job；**推功能分支永远不会上线**。

## 1. 链路

```
push main（paths: presence/** 或 .github/workflows/ci-deploy.yml）
  └ build-check（ubuntu runner，working-directory: presence）
      pnpm install --frozen-lockfile
      shared build → prisma generate → server build → admin build → H5 build
      → miniprogram vue-tsc --noEmit → 打包 admin/h5 dist 为 artifact
  └ deploy（if refs/heads/main && vars.ENABLE_DEPLOY == 'true'）
      runner: 打 server 源码包（apps/server/src|prisma|配置文件 + packages/shared）
      scp 三个 tar 到 ECS /tmp/fullyu-ci
      ECS: 备份旧 dist → 原子替换 nginx 根
           → 解开源码包覆盖 $SERVER_PATH（打平 presence 层）
           → shared build → prisma generate → prisma db push（失败仅告警）
           → tsc 编译 → pm2 restart fullyu-api → curl 127.0.0.1:3000/api/v1/health
```

## 2. 关键事实（决定能怎么发）

| 项 | 值 |
|---|---|
| 仓库 | `git@github.com:531930508-hub/Fullyu.git`（HTTPS remote 无凭据，推送走 SSH key） |
| 部署分支 | `main` |
| 生产入口 | `presence.fullyu.cn` → 120.55.36.3 |
| 后端 | PM2 进程 `fullyu-api`，`$SERVER_PATH=/root/fullyu`，`:3000` |
| 后台静态 | `/opt/fullyu/apps/admin/dist`（nginx `:8080`） |
| H5 静态 | `/opt/fullyu/apps/miniprogram/dist/build/h5`（仅 80 端口 default server 直读，无容器） |
| ECS 上的源码 | **不是 git 仓库**，是从 `presence/` 打平的 rsync 副本；故用源码包覆盖而非 git pull |
| `apps/server/.env.local` | 只在 ECS 上，部署不覆盖；缺失则 deploy 直接失败 |
| 依赖变更 | workflow **刻意不跑 install**；新增/升级依赖必须先在 ECS 手工 `pnpm install`，否则编译或启动会缺包 |
| 数据库 | 仅 `prisma db push`（仓库无 migrations）；**禁止** `migrate dev` / `migrate reset`；push 失败只告警，需人工跟进 schema 漂移 |
| 测试环境 | **4 套，均在 8.133.6.18（上海）**：`test-presence`（:3000）、`test-teahour`（:18788）、`test-crm`（:8897）、`test-cityretreat`（:19929，轻疗测试，2026-11-17 由 `mall-test` 改名）；四套库都在本机 MySQL。**CI 只发生产，测试发布是手工产物覆盖**（§3.7） |

## 3. 标准动作：发布到生产

1. **确认改动范围**：`git status`、`git log origin/main..HEAD`；只带本次改动的提交，别人的未提交改动不动。
2. **本地验证门禁**（等价于 CI 的 build-check，任一红就停）：
   ```bash
   cd presence
   pnpm install --frozen-lockfile
   pnpm --filter @fullyu/shared build
   pnpm --filter @fullyu/server db:generate
   pnpm build:server && pnpm build:admin   # admin 内含 vue-tsc --noEmit
   pnpm --filter @fullyu/miniprogram build:h5
   pnpm --filter @fullyu/miniprogram exec vue-tsc --noEmit -p tsconfig.json
   ```
3. **合并并推送**（`--ff-only`，有冲突就停下来问，不要强推）：
   ```bash
   git checkout main && git pull --ff-only
   git merge --ff-only <feature-branch>
   git push origin main          # 若 HTTPS 无凭据：git push git@github.com:531930508-hub/Fullyu.git main
   ```
4. **盯 CI**：`build-check` 绿 → `deploy` 是否出现。若 `deploy` 被跳过，说明 `ENABLE_DEPLOY` 未开：Settings → Secrets and variables → Actions → Variables。
5. **生效探针**（必做，不能只看"构建成功"）：
   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' https://presence.fullyu.cn/api/v1/health          # 期望 200
   curl -s -o /dev/null -w '%{http_code}\n' https://presence.fullyu.cn/api/v1/<新接口>          # 发布前 404 → 发布后 401/200
   curl -s -o /dev/null -w '%{http_code}\n' https://presence.fullyu.cn/admin/                  # 期望 200
   ```
   CI 日志里的 `health ok` 是必要条件，不是充分条件。

   ⚠️ **后台静态产物以公网 md5 核对为准**：`presence.fullyu.cn/` 自 2026-11-13 起由宿主 nginx 直接 `root /opt/fullyu/apps/admin/dist`，**不再 proxy 到 docker 容器**；2026-11-15 22:56 已把遗留的 `zaichang-web-main-test-8101` 容器停删（它一直绑在被换掉的旧 inode 上，`/home/dist` 为空，`127.0.0.1:8101` 返回 403，属纯僵尸）。
   ```bash
   # 公网取一份带 cb 的 index.html，md5 必须等于宿主文件（绕开本机代理缓存）
   curl -s "https://presence.fullyu.cn/index.html?cb=$(date +%s)" | md5sum
   md5sum /opt/fullyu/apps/admin/dist/index.html
   ```
   📌 **教训仍有效**：任何「目录级 bind mount」的容器，在有人 `mv dist dist.bak-xxx && mkdir dist` 之后都会继续绑旧 inode，用户看到旧版而宿主 md5 正常（11-10 踩过，11-15 复核确认）。以后若要再加这类容器，必须整目录替换后 `docker restart`，并在发布检查里保留「容器内 md5 = 宿主 md5」这一步。
6. **汇报格式**：`目标环境 | commit | CI 结论 | 生效探针前后值 | 回滚命令 | 遗留人工项`。

| `test-teahour` | `/opt/teahour-test/app/apps/server` | `/opt/teahour-test/app/apps/admin/dist` | `teahour-test` / `/etc/teahour-test/api.env` | `https://test-teahour.fullyu.cn/api/health` |
| `test-crm` | `/opt/fullyu-crm-test/apps/server` | `/opt/fullyu-crm-test/apps/admin/public`、`apps/game` | `fullyu-crm-test` / `/etc/fullyu-crm-test/crm.env` | `https://test-crm.fullyu.cn/api/health` |
| `test-cityretreat`（轻疗测试） | `/opt/fullyu-mall-test`（`start-backend.sh` 起 jar） | `/opt/fullyu-mall-test/admin-dist`（占站点根）、`h5`（商城 H5，`/h5/`）、`game` | `test-cityretreat` | `https://test-cityretreat.fullyu.cn/` |

步骤：

1. 按 §3 第 2 步在同一 commit 上构建，记录 `git rev-parse --short HEAD`；**不要用生产 `.env.local`**。
2. 服务器先备份目标目录（保留，不覆盖）：
   ```bash
   ts=$(date +%Y%m%d-%H%M%S)
   tar -czf /root/backups/test-presence-$ts.tar.gz -C /opt/presence-test/app/apps/server dist
   tar -czf /root/backups/test-presence-web-$ts.tar.gz -C /opt/presence-test/app/apps/admin dist
   ```
3. `scp` 到 8.133 的 `/tmp`，解到临时目录后覆盖：后端 `rsync -az <tmp>/server/dist/ /opt/presence-test/app/apps/server/dist/`；静态 `rsync -az <tmp>/admin/dist/ /opt/presence-test/app/apps/admin/dist/`。**不加 `--delete`**（保留微信校验文件/独立落地页）。
4. `systemctl restart presence-test`（其余环境换对应 unit），`systemctl is-active` 必须 `active`。
5. 探针：先 `curl 127.0.0.1:3000/api/v1/health`，再走公网域名；静态用页面 `?cb=$(date +%s)` 取一次，确认新版本。测试库只能是 `fullyu_test` / `teahour_test` / `crm_test` / `tou_mall_test`，**出现生产库连接串就立即停止**。
6. 回滚：解开 `/root/backups/test-<env>-*.tar.gz` 覆盖回去，`systemctl restart <unit>`。

> 2026-11-17 16:20 起：上面 1–5 步已脚本化 —— `deploy/scripts/deploy-test-env.sh`（presence / teahour / crm 三套）：
>
> ```bash
> # 先在同一 commit 上构建，再推产物
> deploy/scripts/deploy-test-env.sh teahour --server <build>/apps/server/dist --admin <build>/apps/admin/dist
> deploy/scripts/deploy-test-env.sh crm     --server <build>/apps/server/dist --admin <build>/apps/admin/public
> ```
>
> 脚本做的事：远端 `tar` 备份到 `/root/backups/test-<env>-<ts>.tar.gz` → 上传 `/tmp` → `rsync -a`（**不加 `--delete`**）→ `systemctl restart` → 本机 + 公网探针 → 打印回滚命令。
> 属主用 `chown -R --reference=<原目录>` 保持服务账号，不动服务器 env。
> **轻疗测试 `test-cityretreat` 不在脚本范围**：它和轻疗生产同源，按轻疗窗口手动做。

## 4. 回滚

- **前端**：ECS `/tmp/fullyu-dist-admin.bak-<ts>.tar.gz`、`/tmp/fullyu-dist-h5.bak-<ts>.tar.gz`（每次部署自动备份，只保留最近 5 份），解包覆盖回去即可。
- **后端**：`/tmp/server-dist.bak-<ts>.tar.gz`（编译产物，同样只保留最近 5 份）或直接回滚 commit 重跑发布（源码包覆盖是幂等的）。
- **数据库**：不做逆向迁移；`db push` 是加列/加表为主，回滚代码时保留新列通常无害。

## 5. 常见坑

- 只推了功能分支 → 线上完全没变，别误判成"已上线"（2026-11-13 导师门户就是这个情况）。
- `origin` 是 HTTPS 且 keychain 无凭据、`gh` 未装 → 用 SSH URL 推送，不要改 remote 配置。
- ECS 内存有限：前端产物必须在 runner 构建后 scp，不能在 ECS 上 build。
- 依赖新增没在 ECS 装 → tsc 能过但运行时缺包。
- 小程序上线不走这条链路：`build:mp-weixin` 后用 `~/.fullyu-secrets/mp-upload/upload.js` 上传，再人工提交审核发布。
  - **必须显式指定产物目录**：`node upload.js <版本> "<备注>" <repo>/presence/apps/miniprogram/dist/build/mp-weixin`。
    脚本默认目录是一份旧副本（`fullyu-platform`），2026-11-14 就是用它上传，导致畅练卡下线后线上一直是老版本。
  - 脚本会对产物做防呆：`app.json`/tabBar 仍注册 `pages/member` 直接拒传。
  - 上传要绕开本机代理（`env -u https_proxy -u http_proxy ... node upload.js`），否则 `unable to verify the first certificate`。
- **`db push` 失败被吞 → 运行期 500**：仓库无 migrations，ECS 上 `db push` 因历史漂移（遗留表/列）必然失败，旧版只 `::warning::`。
  2026-11-15 `orders.card_type` 缺列，登录后拉订单全 500 而部署显示成功。
  现在部署脚本会跑 `prisma migrate diff` 兜底：出现 `ADD COLUMN`/`CREATE TABLE` 即中止部署并打印缺失项。
  线上补列方式（只做 additive，不碰遗留表）：
  `printf 'ALTER TABLE ...' | pnpm --filter @fullyu/server exec prisma db execute --url "$DATABASE_URL" --stdin`

## 6. 待补齐（2026-11-17 修订）

- **有测试环境，但没有自动发布通道**：`test-presence` / `test-teahour` / `test-crm` / `test-cityretreat` 都在 8.133（§3.7），CI 仍只发生产。因此"本地/CI 构建全绿"仍是上生产的唯一门禁；测试环境用来验证，不是发布前置的自动关卡。
- **`ENABLE_DEPLOY` 只管生产**：测试环境的 unit 与库都在 8.133 本机，手工发布不会碰生产。
- **静态验证要绕开本机缓存**：从这台机器 curl 静态 HTML/JS 可能拿到缓存的旧版本（本机代理会缓存甚至伪造 502）。以 ECS 上 `md5sum`/`mtime` 与本地构建产物比对为准。
- `ENABLE_DEPLOY` **当前值 = `true`**（2026-11-15 21:34 在场部署由 CI 自动执行完成，`deploy` job 出现且绿）。若某次推 main 后 `deploy` 被跳过，就是变量被关或改名了，去 Settings → Secrets and variables → Actions → Variables 复核；**不要靠"看起来上了"判断**。
