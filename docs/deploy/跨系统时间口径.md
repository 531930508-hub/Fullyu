# 跨系统时间口径（在场 / 时叙 / 轻疗 / CRM）

> 2026-11-12 实测 + 代码核对。适用于「多系统同机部署、互传数据、共用 CRM」之后。
> 一句话：**统一机器时区和传输格式，不统一库里存什么。**

## 一、结论

| 系统 | 运行时 | 库里存什么 | 跨边界传什么 | 依赖什么 |
|---|---|---|---|---|
| 在场 | NestJS + Prisma 5 / MySQL | **UTC 值** | `toISOString()`（带 `Z`） | 进程 TZ=+08（单号、时区折扣） |
| 时叙 | NestJS + Prisma / MySQL（待迁） | **UTC 值** | 只传 `birthday: "YYYY-MM-DD"` | 进程 TZ=+08（单号日期段） |
| 轻疗 | Spring Boot + MyBatis / MySQL | **北京时间墙钟** | `yyyy-MM-dd'T'HH:mm:ssxxx`（偏移由 `Asia/Shanghai` 生成） | **上报路径已显式 `Asia/Shanghai`**；其余 141 处 `LocalDateTime.now()` 仍依赖进程 TZ=+08 + JDBC `serverTimezone=Asia/Shanghai` |
| CRM | NestJS + Prisma / SQLite→MySQL | **UTC 值** | 接收带偏移 ISO8601；`dayOf()` 把 `YYYY-MM-DD` 当`+08:00` 当日零点 | 进程 TZ=+08（日报日界） |

四套都能自洽跑，因为**边界上传递的是绝对时间**。所以不要"统一存储口径"——那样只能靠改历史数据，收益为零、风险拉满。

## 二、三条硬规则

**R1 机器与进程 TZ 一律 `Asia/Shanghai`，且显式声明。**
不靠默认值。systemd unit 写 `Environment=TZ=Asia/Shanghai`；容器挂 `/etc/localtime` 或设 `TZ=Asia/Shanghai`；JVM 加 `-Duser.timezone=Asia/Shanghai`。
理由：`docker run` 默认给的是 **UTC**，宿主机是 CST 时容器内会差 8 小时，且不会有任何报错。

**R2 跨系统只传两种格式：**
- 瞬间 → 带偏移 ISO8601（`...Z` 或 `...+08:00`），**禁止**无偏移的 `yyyy-MM-dd HH:mm:ss`
- 日期 → `YYYY-MM-DD`，语义固定为「上海自然日」

**R3 不改 RDS 实例 `time_zone`（现值 +08，保持），各库存储口径各自为准。**
MySQL 的 `time_zone` 只影响 `NOW()`/`CURRENT_TIMESTAMP` 和 `TIMESTAMP` 列，不影响 `DATETIME` 字面量存取。轻疗靠数据库默认值生成时间，改实例时区会打偏它的生产数据。

## 三、实测现状（2026-11-12，121.40）

- `timedatectl` → `Time zone: Asia/Shanghai (CST, +0800)`，`NTP service: active` ✅
- 时叙 systemd 只有 `EnvironmentFile=/etc/teahour/api.env`，无 TZ 覆盖 → 继承宿主 CST ✅
- 轻疗 java 裸跑：`java -Duser.timezone=Asia/Shanghai -jar mall-admin-1.0-SNAPSHOT.jar`（2026-11-12 起启动命令显式带 TZ，之前靠默认值）
- 在场报单 `presence/.../brand-presence.sync.ts:300` 用 `toISOString()`；轻疗报单 `BrandOrderReporter.crmTime()`（`BrandOrderReporter.java:62`）把库里的北京墙钟按 `ZoneId.of("Asia/Shanghai")` 拼偏移 —— 两种格式 CRM 的 `eventAt()`（`program.service.ts:68`，`new Date(raw)`）都能正确解析 ✅

## 四、四个炸点（都不是"现在错了"，是"一改就错"）

1. **轻疗把偏移写死成字面量** —— 2026-11-12 已修，保留记录
   原实现 `ofPattern("yyyy-MM-dd'T'HH:mm:ss'+08:00'")` 配 `LocalDateTime.now()` / `Timestamp.toLocalDateTime()`（JVM 默认时区）。
   JVM TZ 一旦变 UTC，报给 CRM 的 `paidAt` 就**早 8 小时**，格式还照样写着 `+08:00`，CRM 照单全收 → 积分账本 `occurredAt` 错、跨天归属错、活跃度统计错。**无声错误。**
   现改为 `BrandOrderReporter.crmTime()`：库里的北京墙钟按 `ZoneId.of("Asia/Shanghai")` 拼偏移（`xxx` 由时区算，不再写字面量），`runOnce` 的基准时间也用 `now(SHANGHAI)`；单测 `crmTimeStaysShanghaiWhenJvmTimezoneIsUtc` 把进程 TZ 切到 UTC 断言仍报 `+08:00`。
   注意：**上报路径独立带时区了，但轻疗其余 141 处 `LocalDateTime.now()` 仍依赖进程 TZ** —— R1 依然必须遵守。
2. **容器化默认 UTC**
   哪天上 docker 而忘了设 `TZ`，直接命中第 1 条。Java 容器尤其隐蔽。
3. **单号里的日期段取进程本地日期**
   时叙 `common/ids.ts:20` `dayStamp()`（`YYYYMMDD`）、在场 `common/order-no.helper.ts:27` `getFullYear/getDate`、`doc-no.helper.ts:21`。
   进程 TZ 变 UTC 后，北京时间 00:00–08:00 下的单会落到**前一天**的号段，财务日报按号段统计就对不齐。
4. **在场时区折扣**
   `presence/.../time-discount.ts` 注释明写「部署时区 Asia/Shanghai，UTC 午夜 = 当地同日 08:00」。它按当地小时判断折扣时段，TZ 变了折扣档位错。
