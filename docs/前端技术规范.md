# Full愈 前端技术规范

> 定位：全平台前端唯一标准。**新代码强制遵守；存量代码冻结，只在改动时顺带收敛。**
> 制定：2026-11。与 `AGENTS.md`（发布/分支规则）配合使用，不替代它。

---

## 0. 一句话决策

**Vue 3 + TypeScript + Vite**，后台用 **Ant Design Vue**，小程序用 **uni-app**；后端 **NestJS + Prisma**；**pnpm monorepo** 统一管理。

三条依据：

1. 五个发布单元里，三个小程序已经是 uni-app + Vue 3，在场后台是 Vue 3；例外只有两处（时叙后台 React、轻疗商城后台 Vue 2）。
2. 一套语言覆盖「小程序 + H5 + 后台 + 服务端」，类型可跨端共享，这是 React 给不了的。
3. 全部是主流、有社区、招得到人的技术，没有实验性框架。

## 2. 版本基线

| 项 | 基线 |
|---|---|
| 语言 | TypeScript 5.x，`strict: true` |
| 框架 | Vue 3.4+，一律 `<script setup lang="ts">` + Composition API |
| 构建 | Vite 5+ |
| 后台 UI | Ant Design Vue 4.x（唯一组件库） |
| 状态 | Pinia |
| 路由 | vue-router 4（后台 hash 模式） |
| 小程序 | uni-app（Vue 3 编译器） |
| 样式 | Less（AntD 主题变量）+ `packages/design-tokens` |
| 包管理 | pnpm 8+，锁文件只有 `pnpm-lock.yaml` |

硬规则：

- **禁止引入第二套组件库**（Element Plus、Naive UI、Vuetify、Vant 桌面版一律不许）。
- **禁止新增 jQuery 或手写 DOM 操作**（CRM 存量随换壳消失）。
- 新增依赖必须在 PR 描述里一句话说清「为什么现有能力做不到」。
- 不用 Vuex、不用 Options API 写新组件、不用 `mixins`。

## 3. 后台目录与分层

```
apps/admin/src/
  shell/                 # 布局、登录、菜单装配、权限指令、请求层、表格/表单基座
  modules/
    platform/            # 账号、角色、组织门店、字典、审计、待办
    crm/                 # 会员积分
    scm/                 # 进销存
  stores/                # 仅放跨模块状态；模块内状态留在模块里
```

规则：

1. **模块自包含**：`modules/<name>/` 下自带 `manifest.ts`、`api.ts`、`views/`、`components/`、`types.ts`。
2. **壳不反向依赖**：`shell/` 不得 import `modules/*/views/*`。
3. **模块之间不互相 import**：共享的东西下沉到 `shell/` 或 `packages/shared`。
4. **新增模块 = 新增目录 + 注册一行**，不改壳的其他文件：

```ts
// modules/<name>/manifest.ts
export default {
  id: 'scm',
  name: '进销存',
  order: 20,
  routes: [/* 懒加载 */],
  menu: [/* 分组 + 条目，条目带 perm */],
  permissions: [/* { code: 'scm:stock:adjust', name: '库存调整' } */],
}
```

---

## 4. 权限

- 权限码格式 `<module>:<resource>:<action>`，例：`crm:member:view`、`scm:stock:adjust`、`platform:role:edit`。
- 权限码**只在模块 manifest 声明一次**，角色勾选树由它生成，禁止前端各处硬编码字符串。
- 前端用 `v-perm` 指令和路由 `meta.perm` 控制可见性；**只做体验，服务端必须逐请求校验**。
- 门店/部门数据隔离由服务端守卫注入过滤条件；**前端传的 `orgId` 不能作为授权依据**。

---

## 5. API 与请求层

- 后台接口 `/api/<module>/...`；`/api/external/*` 是三端小程序的对外契约，**不得改名、不得改签名**。
- 请求层单例统一处理：baseURL、Bearer 注入、401 跳登录、错误提示、分页参数 `page/pageSize`。
- 组件内禁止直接 `fetch` / `axios`。
- 响应类型放 `packages/shared` 或模块 `types.ts`；业务对象禁止用 `any` 穿透。

---

## 6. 路由与部署

- 后台用 `createWebHashHistory`，`vite base: '/admin/'` —— 免 nginx rewrite，产物同源托管，不额外起静态服务器。
- 构建产物由后端或 nginx 同源发布，路径前缀与 `base` 必须一致。

---

## 7. 质量门禁

- `vue-tsc --noEmit` 与 `tsc --noEmit` 必须通过。
- 提交前跑 lint；`@ts-ignore` 必须写原因或改成 `@ts-expect-error`。
- 模块 manifest 的权限码需与后端 `Permission` 表一致（权限表化完成后由 CI 校验）。

## 9. 决策记录：为什么是 Vue 3 而不是 React

| 维度 | Vue 3 | React 18 | 对本平台的意义 |
|---|---|---|---|
| 心智模型 | 响应式自动追踪（Proxy），模板编译优化 | hooks，需要手动管依赖数组、闭包、memo | Vue 上手快，中后台页面多、人员流动大时更省心 |
| 类型 | `<script setup lang="ts">` + vue-tsc | 类型即 JS，TS 生态最成熟 | 两者都够用；React 略强，但不构成决定性差距 |
| 生态 | 国内中后台强（Ant Design Vue / Element Plus / vben） | 组件库与招聘池更大 | 你的场景不需要 React 独占的库 |
| 性能 | 编译期优化，默认够用 | 需要手动优化（memo/useMemo） | 中后台不是性能瓶颈；小程序才是，而 uni-app 只走 Vue |
| 跨端 | uni-app 原生 Vue 3 | React Native 不覆盖微信小程序 | **决定性**：一套语言覆盖小程序 + H5 + 后台 |
| 存量 | 在场后台 + 三个小程序已是 Vue 3 | 仅时叙后台 11 个 tsx | 选 Vue 3 的重写量最小 |

结论：React 与 Vue 3 不存在「先进/落后」，只有取舍。以「一套技术覆盖最多端、最少重写」为标准，本平台选 Vue 3。
