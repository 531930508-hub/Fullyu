## 0. 一句话

**老小程序直接连新后端，不用改老端。** 29 个只读接口逐字段比对零差异、下单/资料修改/聊天/评价实测通过、支付返回契约未变。上线动作本身就是：**跑一批纯增量的 SQL → 换 jar → 重启**。

风险只有一条真实存在：**重启期间 1~2 分钟不可用**（生产日志实测 jar 启动 23~25 秒，余量留给预热）。

## 2. 已验证结论（含复现命令）

### 2.1 契约 A/B：29 个只读接口，零差异

做法：生产今天的数据全量副本 → 新 jar 跑在本机 → 同一个 token、同一套真实参数，同时打**生产旧后端**和**新后端**，逐层比 JSON 结构+类型。

| 结果 | 数值 |
|---|---|
| 只读接口总数 | 29 |
| 字段消失 | **0** |
| 字段类型变化 | **0** |
| 差异类型 | 只有「新后端多返回字段」（`memberCardId`/`memberRate`/`benefitAmount`/`priceSource`/`identities`/`receptionCapPercent` 等），老端读不到也不受影响 |
| 天然报错的 4 个接口 | 送礼分享码、`order/timeList` 参数不全、`order/checkout`、`admin/open/wx/*` —— 两边返回**完全相同**的业务错误码与文案 |

复现：

```bash
# 在测试机（副本后端跑在 127.0.0.1:19399）
ssh mall-test 'AB_PHONE=<内部测试号> python3 /opt/fullyu-mall-test/tmp-ab.py login'   # 拿 token
# 该 token 需同时存在于两侧 Redis：生产 db1 临时写入（TTL 1200s，用完即删）
ssh root@120.55.36.3 "redis-cli -h 47.111.136.49 -n 1 SET 'loginToken:<token>' <customerId> EX 1200"
ssh mall-test 'AB_PHONE=<内部测试号> python3 /opt/fullyu-mall-test/tmp-ab.py run'      # 输出 /tmp/ab-report.json
ssh root@120.55.36.3 "redis-cli -h 47.111.136.49 -n 1 DEL 'loginToken:<token>'"       # 务必删掉
```

> 脚本已固化进仓库：`tou-mall-server/scripts/contract-ab.py`（放到测试机执行）。
> 之所以要往生产 Redis 写一条 `loginToken:`，是因为 `SessionService.getCustomerId()` 是「JWT 有效 + Redis 有会话」双重校验，只写 Redis、TTL 20 分钟、用完即删，不产生任何业务数据。

### 2.4 冷启动

| 场景 | 耗时 |
|---|---|
| 生产日志里同款 jar 的历史启动记录（4 次） | **23.1s / 22.2s / 23.5s / 24.5s** |

### Step 2｜挂维护页

⚠️ **不要新建第二个 `location /api/ {}`** —— nginx 会报 `duplicate location`，`nginx -t` 失败、reload 被拒，你以为挂了维护页其实线上没变。

一次性在 `fully.conf` 的 `location /api/ {` 里加一行 include（之后每次维护只切文件）：

```nginx
location /api/ {
    include /etc/nginx/maintenance/api-maintenance.conf;   # 只加这一行
    proxy_pass http://localhost:9929/;
    ...
}
```

```bash
mkdir -p /etc/nginx/maintenance && : > /etc/nginx/maintenance/api-maintenance.conf
nginx -t && nginx -s reload          # 空文件，行为不变

# 开维护
cp docs/ops/api-maintenance.snippet /etc/nginx/maintenance/api-maintenance.conf
nginx -t && nginx -s reload

: > /etc/nginx/maintenance/api-maintenance.conf && nginx -t && nginx -s reload
```

## 6. 回滚（三级，从轻到重）

| 级别 | 触发条件 | 动作 | 耗时 |
|---|---|---|---|
| **L1 只回 jar** | 启动失败、探活不过、日志出现 Unknown column / 500 潮 | `cp backup/$TS/mall-admin-1.0-SNAPSHOT.jar .` → `bash stop-120.sh && bash start-120.sh`；或一条命令 `scripts/rollback-prod-code.sh --jar-dir <TS>`（自带远端身份校验） | 1min |
| **L2 回 jar + 关新入口** | 新功能菜单报错但主流程正常 | L1 + 撤掉新菜单（菜单由 SQL 插入，可 UPDATE 隐藏，不必删） | 5min |
| **L3 回库** | 几乎不会发生 | 走 RDS 快照恢复 | 30min+ |

**为什么 L1 就够**：本批 SQL 纯增量（新表 + 新列，新列都有默认值/可空），老 jar 不认识这些表和列，多出来不影响它。**唯一要注意**：`s_order` 的 `visit_no` 回填、菜单新增记录改了数据但不改结构，老 jar 忽略即可。

## 11. 前端 dist 发布闸门（2026-11-20 起强制）

### 11.1 只能这样出产物

```bash
node qingliao/tou-mall-admin-web/scripts/release-dist.mjs --env prod   # 生产，BASE_API=https://manage.fullytherapy.com/api
```

脚本做四件事，任何一步不过就退出非 0、不产出包：

1. 只接受 `origin/main` 上的提交（默认就是 `origin/main`；`--commit` 也必须已在 main 里），且该提交之后 main 没有落下的 `src/` 改动；
2. `git archive` 干净导出后构建——工作区未提交的改动进不了产物（看板就是这么漏出去的）；

4. 写 `dist/static/build-info.json`（commit / env / baseApi / entry / builtAt）。

### 11.2 部署后必须回读

```bash
curl -s https://manage.fullytherapy.com/static/build-info.json   # 生产
curl -s https://test-cityretreat.fullyu.cn/static/build-info.json # 测试
```

`commit` 必须等于本次上线记录里写的提交；对不上就是发错包。上线记录里同时写入口 hash（`grep -o 'app\.[a-f0-9]*\.js' dist/index.html`）。

### 11.3 功能标记的维护

- 新增功能：在 `release-markers.tsv` 加一行「标记<TAB>功能/提交」，标记要选压缩后仍在的字符串字面量（中文文案、`tel:`、`payAmount:null`），不要用纯标识符。
