### 0. V5.1 源码实现与月份切换（2026-10-21）

本轮已按确认规则在现有工程中编写源码、SQL 迁移、JUnit 与开发交接说明；**未 commit、未部署、未修改生产数据库或线上服务**，也未在本机完成 Java 编译与前端整包构建。

- **手机端月份切换**：疗愈师可点击上一月/下一月，或使用原生月份选择器；不允许选择未来月份，并提供“回到本月”。切换后看板全部数据按所选月份重算。
- **截止口径**：当前月统计至今天；历史月统计至该月最后一天。手机页明确显示“当前月份 · 数据统计至 X”或“历史月份 · 数据统计至月末 X”。
- **统一按月**：基础接单分钟与系数、培训项目进度与达标月、复购留存/30 天档位/10 天复购、门店业绩与店长奖励、合作结算明细，均使用同一个所选月份与同一截止日，避免跨月混算。
- **培训**：仍从通过考核次日起累计；历史月按截至月末的订单快照判断达标，未来完成的订单不会回算到历史月。
- **复购归属**：10 天复购与 30 天档位仍按客户首单月归属；历史月只读取截至月末已发生的到店记录。由此带来一个待产品确认的边界：月末首单客户的第二次到店若发生在次月，历史月快照不会看到该记录。若要求完整观察 10 天/30 天窗口，应把“统计截止”拆成“展示截止＝月末”与“观察截止＝月末+N 天”，同时仍把奖励归属首单月；当前实现遵循用户明确的“算到月末”口径，未擅自扩展观察窗。
- **权限**：门店范围、仅本人范围和全局角色均由服务端校验；导出入口只对全局角色显示，保存参数、考核记录与门店目标在服务端再次校验。

### 1. 培训补贴：8 个独立项目

| 组别 | 独立项目 | 计数口径 |
|---|---|---|
| 全感舒筋 | 面部、手部、头部、肩部、眼部、腿部，共 6 项 | 每项分别累计；只计对应部位的本人有效服务 |
| 头部水疗 | 60 分钟、90 分钟，共 2 项 | 时长必须精确匹配；60 与 90 分钟不得互相计数 |

- 每一项可分别设置“完成订单次数”和“补贴金额”；当前默认均为 **5 次 / ¥500.00**。次数为 1–999 的整数，金额为不小于 0 的数值。
- 疗愈师的通过日期按“人 × 项目”维护在管理端独立的“培训项目与考核”视图，不在手机端编辑。原型把维护入口放在该独立视图；正式接入可复用现有培训/认证后台，看板只读取结果，避免出现两套通过日期来源。没有通过记录的项目不累计、不产生补贴。
- 起始日固定为 **通过日期次日**。通过当天的订单不计入；例如张三 2026-02-03 通过舒筋-头部，从 2026-02-04 起累计头部有效订单。
- 统计截止：历史结算月取月末；当前月取数据截止时间与月末中较早者。原型当前月使用今日作为截止，页面标明预估状态。

```text
起始日 = 通过日 + 1 天
截止日 = 历史月 ? 月末 : min(数据截止, 月末)
达标日 = 起始日至截止日内，第 N 条对应项目有效订单的日期
本月培训补贴 = 达标日所在月 == 结算月 ? 该项目金额 : 0
```

- 只计有效服务订单：已付款、已到店/已完成、`pay_time` 非空；0 元有效服务不排除，购券订单不算到店。正式接入还须限定服务伙伴本人、项目/部位与头部水疗时长。
- 补贴只在**达标订单所在月**计入一次。若 5 月达标，5 月计入；6 月及以后显示“此前已达标，已计入历史月份”，不重复计入。达标月份已结算后才补录的订单，不把补贴自动顺延到当前月，应进入结算差异/补发处理。
- 同一位伙伴的不同项目互不影响；修改通过日期会按新起点重算尚未冻结的进度、达标日和金额。原型保存后立即重算，并以本地配置持久化。
- 生产兑现需生成唯一凭证：伙伴 × 项目 × 通过事件唯一；凭证冻结通过日、目标次数、达标订单 ID/日期、金额与规则版本。重复同步、重复打开或重复提交不得重复发放；若通过日修订后影响已冻结月份，只能生成调整凭证，不删除历史。

示例：目标 5 次、金额 ¥500。2 月 4 日起累计，若第 5 单发生在 2 月 20 日，则 2 月计入 ¥500，3 月为 0；若第 5 单发生在 3 月 2 日，则 2 月为 0，3 月计入 ¥500。

### 2. 基础接单系数：达到起点即跳档

| 月折算上钟分钟 m | 系数（元/分钟） |
|---|---:|
| 0 ≤ m < 7,200 | 1.0 |
| 7,200 ≤ m < 8,400 | 1.2 |
| 8,400 ≤ m < 9,600 | 1.3 |
| m ≥ 9,600 | 1.5 |
| 新伙伴适用期 | 0.8 |

- 区间左闭右开；**达到 7,200 / 8,400 / 9,600 的当刻就进入更高档**，不再沿用“端点仍属前一档”。
- 基础接单奖励仍为“全月折算分钟 × 所在区间单一系数”，不分段累加：7,200 分钟 = 7,200 × 1.2 = ¥8,640.00；8,100 分钟 = ¥9,720.00；8,400 分钟 = ¥10,920.00；9,600 分钟 = ¥14,400.00。
- 新伙伴适用期继续沿用既有 `formal_month` 等识别规则，不根据加入日期另造一套判断。
- 原型引擎、手机阶梯、PC 参数表与试算均已按左闭右开实现；改参数后手机端通过链接快照或同源存储同步。
- 正式落地前仍需核对真实 `s_salary_coefficient` 配置的最高上界与 `getSalaryCoefficient` 取值行为。现有函数对“超过所有配置上界”的情况可能存在回退首项的风险，不能把原实现直接照搬，也不能声称生产端已经修复；原型第四档按开放上界展示。

### 3. 管理端：看板与培训记录同页管理

- 看板默认展示 5 张指标卡：本月接单奖励合计、复购、店长、培训、预计合作结算；培训合计取“本月达标项目 × 各自金额”。默认样本为 18 条已登记考核、48 个可登记项、4 项本月达标，合计 ¥2,000.00。

- 记录表列为：疗愈师/门店、培训项目、通过考核日、累计起点、有效订单进度、达标日期、本月补贴、状态、操作。筛选支持门店、项目、状态、姓名与重置；未登记状态按“伙伴 × 项目”展开。
- 新增/编辑弹窗可登记通过日并实时预览进度；编辑时锁定伙伴与项目。通过日限制在加入日期至今日之间。保存后按人和项目合并，不产生同一人同一项目的并行有效记录。
- 参数设置“培训项目”页提供 8 行独立次数与金额，保存后生成新版本并同步看板、培训页与手机预览；若各项相同，版本摘要显示“8 项统一 5 次 / ¥500.00”，若不同则显示独立参数。

### 页面顺序

1. 身份信息 → **累计成就常显**：加入日期、加入天数、累计服务分钟、去重服务客人数、头号粉丝及脱敏号码。取消全部/近30天/近90天/今年和日期滑杆；累计口径截至今日。手机月份改为本月文字标签，不提供时间筛选，PC 的历史月份功能不受影响。
2. **本月接单奖励合计**：保留唯一主金额与金额隐藏开关。
3. **基础接单奖励**：金额在卡片标题右侧；下方直接显示当月折算上钟时长、当前系数与四档阶梯线。
4. **复购接单奖励**：标题右侧为两类合计；卡片内依次常显老客60天留存率、新客30天复购率及五档阶梯、30天计入金额、新客10天递增金额与下一位提示。
5. 店长接单奖励（仅本人为店长时）、统一培训补贴；计算说明、统计口径、合作结算、项目认证仍折叠，内容保留。

### 时长阶梯

- 主指标按小时展示，附本月折算分钟，明确不同于累计成就中的原始服务分钟。
- 阶梯点对应四档：≤120小时、>120小时、>140小时、>160小时；系数从既有配置读取，默认1 / 1.2 / 1.3 / 1.5元/分钟。
- 以原始分钟决定当前档。**V4 历史文案曾写“7200 / 8400 / 9600 分钟端点仍属前一档”；V5 已改为达到起点即跳档，现行规则见顶部 V5 节。** 135 小时示例显示第二档 1.2 元/分钟，按 V5 规则再累计 300 分钟到 8,400 分钟即进入第三档。
- 节点高亮和“当前档”文字共同标识位置，不仅依赖颜色。连线表达离散档位顺序，并非等比例时长坐标。
- 新伙伴适用专属系数时明确展示0.8元/分钟等实际配置；标准阶梯只作参考，不高亮为已解锁档。

### 复购常显与状态区分

- 老客60天留存率直接展示百分比、门槛和达标状态；它仍是两类复购奖励的共同前提。
- 30天阶梯默认展示10% / 12% / 15% / 18% / 20%及各档金额，突出当前位置。阶梯值使用当前配置，不另行硬编码奖励金额。
- 留存未达或新客样本不足时，仍可观察比例所在节点，但用空心节点和“指标所在档 / 尚未计入”区分；两类奖励是否计入仍按原规则执行，小样本只单独限制30天档位。
- 百分比向下保留两位展示以避免临界值显示成已达标；实际判断沿用引擎未舍入值。无分母显示“—”，不伪造有效比例。
- 下一档提示显示所需人数与**至少**增加的金额。离散人数可能跨档，例如7/45增加两位会直接到20%，最终取最高档1500元，不固定在18%档。
- 10天递增金额与30天金额分开展示，并保留“下一位可再增加”提示。斐波那契单价、封顶、权重、首单月归属均不变。
- 金额开关隐藏主金额、各项金额及阶梯金额，但保留时长、比例与人数，重绘保持展开区和焦点。

### B. 手机端：统一金额口径，服务指标另放

默认页面仅展示：

1. **本月接单奖励合计**：唯一主金额，示例 ¥10,790.00；仅汇总基础、店长、培训和已满足条件的复购奖励，不将合作结算结果混作同一口径。
2. **奖励构成**：基础接单奖励、店长接单奖励（仅店长本人）、培训补贴、复购接单奖励。每行只放名称和金额，金额统一以元显示并保留两位小数；不将分钟、比例、人数塞在金额旁边。
3. **下一位复购提示**：新客 10 天内再来一次，接单奖励可再增加 +¥50.00。未满足留存条件时明确“满足留存条件后可增加”，不会承诺立即计入。
4. **三个默认折叠的说明入口**：奖励计算说明、复购数据与规则、合作结算明细。
5. **我的服务**：累计成就、项目认证两个默认折叠区，与金额区域分开。

内容不删：累计成就仍包含加入日期/天数、全部/近30天/近90天/今年时间轴、服务分钟、去重客人数、头号粉丝与脱敏号码；项目认证仍含认证日、认证后服务次数、范围终点回望近30天次数。时间轴仍只影响服务记录，不改变月度奖励。

复购比例、分子分母、30 天下一档及差额、所有档位、窗口与数列规则均移入“复购数据与规则”。基础系数、部位数、店长业绩/目标/百分比移入“奖励计算说明”。详细区内部也区分“比例与人数”和“奖励金额”。

**合作结算明细**保留原计算链：接单奖励合计 → 其他调整及记录 → 调整后合计 → 服务费换算差额 → 费用换算后金额 → 预扣税额 → 预计合作结算。年度累计与税费依据继续可展开查看，不删除计算能力、不再把两个口径的总额同时置顶。

金额隐藏开关覆盖全部可见及折叠内容；切换后保持已展开区域和焦点，避免为了隐藏金额丢失阅读位置。模拟身份/事件工具仍仅用于评审，不进入正式页面。

### C. 文案边界

新手机页面、标题、按钮、空态、演示提示、动态状态、折叠详情全面移除：收入、薪酬、薪资、工资、奖金、报酬、到手、应发、实发，以及此前约定的雇佣类词汇。金额使用“接单奖励”，对账流程使用“合作结算”，税费依法保留必要计算说明。

内部已有服务名、数据库字段和变量名不因文案调整而改名。文字替换不等于对合作模式法律性质作出认定；本原型不宣称仅改名称即可保证法律合规。

### D. 店长提点：百分比配置

```text
实际业绩 < 整店目标：店长接单奖励 = 0
实际业绩 ≥ 整店目标：店长接单奖励 = ROUND(整店实际业绩 × commissionRate / 100, 2)
```

- 每店保留月目标，将原 `reward` 固定金额替换为 `commissionRate` 百分比；允许 0–100%，可填小数，0 表示暂不计提。
- 示例：目标 ¥200,000，实际业绩 ¥216,800，提点 1% → ¥2,168；提点 1.25% → ¥2,710。
- 刚好完成目标时也对全部实际业绩计提；低于目标时为零。留存率条件只控制复购，不额外控制店长提点。
- PC 门店卡、伙伴报表、抽屉、导出和手机说明全部使用同一公式；设置输入后即时显示试算。店长本人只读参数，维护权限仍归管理角色。
- 百分比与目标均为示例。业绩数据来源、多店/多位店长归属等原接入边界仍需核定，不在本轮增加未经确认的分摊逻辑。

正式 `s_shop_incentive_target` 设计中的 `reward_amount` 应改为 `commission_rate`，同时在计入凭证冻结实际业绩基数、比例、目标判断和最终金额。旧版固定金额历史记录保留原规则，不直接迁移重算。

### E. 培训补贴：所有部位共用一个金额（已被 V5 取代）

> 本节仅保留 V3 历史方案。现行规则为全感舒筋 6 个部位各自独立、头部水疗 60/90 分钟各自独立，共 8 项，分别设置次数与金额，并从通过次日起累计订单；详见顶部 V5 节。

```text
培训补贴 = 本月首次通过且未重复计入的有效部位数 × trainingAmount
```

- 原分部位金额设置移除，只有一个“每个部位补贴（元）”输入框。
- 示例统一 ¥100：头部+肩颈 = ¥200；头部+眼部也 = ¥200；三个不同部位 = ¥300。
- 修改统一金额为 ¥150 后，全部部位同步使用 ¥150，不需逐项修改。
- 0 元允许作为暂不计补贴配置；负数和无效值拒绝。重复部位、未知部位不重复/错误增加金额。
- 保留部位字典与认证事实，但字典不再各自存金额；正式金额参数保存到规则版本，认证计入凭证冻结应用版本与金额，旧月份不受新值影响。

斐波那契 a1=a2=10、每位单价封顶后继续累计、共同服务权重、首单月归属、60% 留存共同前提、30 天五档不叠加、样本条件、基础折算分钟系数、服务费和个税计算均不因本次展示简化而改变。原 SQL/身份隔离/退款与结算冻结等技术约束继续作为接入参考；以下历史记录凡与 V3 页面、文案或配置冲突，以本节为准。

- 留存率及条件状态；未满足时明确“两类复购激励暂未计入”。
- 新客 30 天复购率及当前档位金额；新客 10 天加权人数及递增累计。
- 主激励提示：“再有一位新客 10 天内回来，可再增加 +¥50”，辅行“下一位 · 第 5 位”。条件未满足时改成“满足条件后可增加”。
- 下一档：例如当前 7/45、15.56%，当前 800；达到 18% 升至 1100，增加 300；在分母不变时还需 2 位。继续达到 20% 可进入 1500 档。
- 各档全表、数列与统计窗口收进“查看规则”，不把完整阶梯铺成主视觉。

“+金额”指该类激励基准，不承诺税后一定增加同额。共同服务权重不为 1 时按该位单价乘实际权重；下一位主提示默认完整归属一位，旁边有分摊说明。

### 4.3 收入与结算明细

依次显示：激励合计、其他调整及明细、结算基数、服务费换算差额、税前收入、当月个税、预估税后收入。年度累计、应纳税所得额、连续月数、税率、速算扣除数、此前已缴税放在折叠区。

用户无需跳到原 PC 明细页。历史已确认月份必须展示冻结结算结果；当月展示估算，不将估算伪装成可领取金额。

原页面存在每月 11 日前对普通伙伴隐藏上月金额的逻辑。新页面正式接入不得无意取消：当前月允许展示标明状态的估算，历史结算按既有发布控制，未发布显示“结算整理中”。原型只有 9 月已发布示例、10 月预估和 8 月无记录，不模拟未发布流程。

### 4.4 项目认证：保留内容

项目名、认证通过日、认证次日起服务次数、以时间轴终点回望近 30 天的次数全部保留，并与时间轴联动。没有认证日的项目不展示。

项目认证次数用于服务能力积累；部位培训认证用于一次性补贴，两者分开，不按项目次数重复发放补贴。

## 5. 计算规则

### 5.1 基础接单奖励：沿用真实代码

现有 `SalaryRecordService.saveBatchSalaryRecord` 使用 `StatisticsService.serviceDuration` 返回的 `totalWorkingHours`（折算工时），选取系数后计算全月金额。

| 月折算上钟分钟 m | 默认系数（元/分钟） |
|---|---:|
| 0 ≤ m < 7,200 | 1.0 |
| 7,200 ≤ m < 8,400 | 1.2 |
| 8,400 ≤ m < 9,600 | 1.3 |
| m ≥ 9,600 | 1.5 |
| 新伙伴适用期 | 0.8 |

现行 V5 口径为左闭右开：达到 7,200 / 8,400 / 9,600 的当刻即进入更高档。现有新伙伴/正式合作月的识别继续沿用 `formal_month` 等既有规则，不根据新加的加入日期另猜。

`基础接单奖励 = 全月折算分钟 × 当前区间系数`，不分段累加。7,200 分钟为 8,640 元；8,100 分钟为 9,720 元；8,400 分钟为 10,920 元；9,600 分钟为 14,400 元。

注意：V5 原型按用户最新确认的左闭右开规则实现，但生产端 `getSalaryCoefficient` 与数据库 `s_salary_coefficient` 的实际取档方式、最高上界仍是待核项。现有函数按上界升序取第一个覆盖值，超出所有上界时存在回退首项的行为；正式实现前必须修正并覆盖端点测试，不能把原函数边界隐患照搬或声称已经修复。原型第四档依据用户确认做开放上界。

### 5.2 复购共同前提与窗口

令结算月为 M：

- 老客窗口长度 6 个月，末月为 M−2；2026-10 对应 2026-03～08。
- 新客 30 天档位统计窗口长度 3 个月，末月为 M−1；2026-10 对应 2026-07～09。
- 10 天递增按 M 月首单客归属；次月完成符合条件的二次到店仍归首单月。
- 留存率 = 窗口内老客服务人次中、后续 1–60 天再到店的人次 / 老客服务人次。
- 30 天率 = 新客窗口内加权 30 天复购数 / 加权新客数；跨月汇总先加分子分母，不平均每月百分比。

用未四舍五入比例判断条件；59.99% 不因页面显示 60.0% 自动计入。分母为零时正式响应返回无样本状态，而非无依据地认定满足条件。

观察期未结束会影响结果，当前月份注明数据截止和预估状态。窗口不足、样本较少不能被解释为自动豁免。

### 5.3 30 天档位

新客样本 ≥30 时，从满足的档位中取最高金额。档位率与金额后台可配；档位率必须严格递增，金额不可递减。最终计入值：

```text
30天计入 = 留存条件满足 ? 最高符合档位金额 : 0
```

下一档需要人数按当前分母不变试算。真实加权数据可能包含 0.5 等权重；正式界面应说明“完整归属的新客复购”，不能把加权缺口无条件说成实际几名客户。

### 5.4 10 天递增与单价上限

```text
a(1)=10，a(2)=10，a(n)=a(n−1)+a(n−2)
p(n)=min(a(n), cap)
潜在10天金额 = Σ [w(n) × p(n)]
10天计入 = 留存条件满足 ? 潜在10天金额 : 0
复购激励 = 30天计入 + 10天计入
```

计算实现可在数列到达上限后停止增长，避免生成无意义大整数；对非负递增种子，这与逐项取 min 等价。

原型 cap=130 时实际单价为：10、10、20、30、50、80、130、130、130……。

| 例子 | 金额与下一位 |
|---|---|
| 4 位完整归属 | 70；下一位第 5 位 +50；累计可达 120 |
| 3 位完整 + 第 4 位权重 0.5 | 55；下一位仍为第 5 位 +50 |
| 4 位完整 + 第 5 位权重 0.5 | 95；下一位第 6 位 +80 |
| 9 位完整、cap=130 | 590；第 10 位再加 130，累计 720 |
| 9 位完整、cap=100 | 500；后续每位继续加 100 |

顺位沿用 v1.2 方案：每条符合条件的新客复购归属记录占一个整数位次，权重只乘金额、不占半序位；同日达成按客户唯一标识稳定排序。月内 `headCount`、`weightedHeads` 必须分开存/传，不能用加权人数直接计算下一位序号。正式结算还需保证跨次计算排序稳定，并冻结结算时的记录与顺位。

### 5.5 店长、培训与去重

- 店长：按门店/月/店长归属和已生效目标规则生成计入依据。未完成目标为 0；完成后按整店实际业绩 × 已生效百分比提点，四舍五入到两位。经理身份不由前端传参决定，店长只读参数。
- 培训：按 V5 的 8 个独立项目保存伙伴、项目、通过时间、审核人、次数/金额规则版本与撤销记录。从通过次日起累计对应项目有效订单，第 N 单所在月计入一次；同一伙伴 × 项目生成唯一兑现凭证，重复同步、重新打开页面或重复提交均不能重复计入。旧月份不套用新参数。
- 原 `otherAmount` 如果已有人工录入的培训/店长款项，分类迁移时保留来源 ID 并排除重复。不得一边显示分类奖励，一边又把同一笔全额留在其他调整里。

### 5.6 统一结算金额链

```text
激励合计 = 基础 + 店长 + 培训 + 已满足条件的复购
其他调整 = 既有正负调整中未被上述分类覆盖的记录之和
结算基数 = 激励合计 + 其他调整
税前收入 = max(0, HALF_UP(结算基数 / 1.068, 0))
服务费换算差额 = 结算基数 − 税前收入
税后收入 = 税前收入 − 本月应缴个税
```

个税继续由既有服务端计算：连续历史劳务报酬加本月税前收入，累计×80%−连续月数×5,000 得到非负应纳税所得额，按累进税率和速算扣除数计算累计税，再减此前已缴，最低为 0。

既有服务有 2026-08-01 创建日期过滤和连续月份/11 月边界等特殊逻辑。本轮未修改这些逻辑，原型的历史累计数为模拟；正式手机页必须消费同一结算服务返回值，不在浏览器或新接口复制另一套税。预扣/上月退回目前为 0 的既有字段也不在本设计擅自新增制度。

默认张小雨示例核对：

```text
基础 8,100×1.2                         = 9,720
培训：肩部 5/5 达标 × 500              =   500
复购：30天800 + 10天70                 =   870
激励合计                              =11,090
其他调整：120−20                      =   100
结算基数                              =11,190
税前：ROUND(11,190/1.068,0)            =10,478
历史模拟税前18,000 + 本月10,478         =28,478
应纳税所得额：28,478×0.8−3×5,000       = 7,782.40
本月税：ROUND(7,782.40×3%,2)−132       =   101.47
税后预估                              =10,376.53
```

### 5.7 退款：预估重算不等于已结算回冲

未锁定估算可依据有效订单变化重算复购资格、顺位与金额，必要时寻找下一个仍有效的二次到店，而不是一律删除该客户归属。

已确认结算不得直接删除旧记录、重排后覆盖历史账单。按原文次月回冲方向生成差额调整，关联原结算、原复购凭证与退款事件，并保留审计。部分退款、退款申请中/审批中、全额退款应分别判定；仅凭状态码排除全部退款流程，不能声称已经正确实现部分退款和结算回冲。

v1.2 中“实时剔除等价次月扣除”“无需手工扣减即完成回冲”的表述作废。本原型未模拟真实退款账本。

### 6.2 公共数据集：设计 SQL 片段

以下以 MySQL 8 CTE/窗口语法表达统计关系；不是可直接投产的完整 Mapper。若实际数据库版本不支持，需改为等价派生表/预聚合并验证执行计划。下列片段只描述无退款争议的已付款有效服务主路径，退款事件还必须结合 §5.7。

```sql
WITH valid AS (
  SELECT o.id AS order_id, o.shop_id, o.pay_time,
         DATE(o.pay_time) AS d, c.phone
  FROM s_order o
  JOIN c_customer c ON c.id = o.customer_id
  WHERE o.pay_time IS NOT NULL
    AND o.state IN (1, 2)
    AND o.appointment_state IN (1, 2)
    AND o.type = 0
    AND c.phone IS NOT NULL AND TRIM(c.phone) <> ''
    AND NOT EXISTS (
      SELECT 1 FROM s_stat_internal_account i
      WHERE i.enabled = 1 AND i.phone = c.phone
    )
), visits AS (
  SELECT DISTINCT phone, d FROM valid
), services AS (
  SELECT DISTINCT v.phone, v.d, od.massagist_id
  FROM valid v
  JOIN oms_order_detail od ON od.order_id = v.order_id
  WHERE od.state IN (1, 2) AND od.massagist_id IS NOT NULL
), first_visit AS (
  SELECT phone, MIN(d) AS first_d FROM visits GROUP BY phone
), second_visit AS (
  SELECT f.phone, MIN(v.d) AS second_d
  FROM first_visit f JOIN visits v
    ON v.phone = f.phone AND v.d > f.first_d
  GROUP BY f.phone
), credit AS (
  SELECT t.phone, t.massagist_id,
         1.0 / COUNT(*) OVER (PARTITION BY t.phone) AS w
  FROM (
    SELECT DISTINCT s.phone, s.massagist_id
    FROM services s JOIN first_visit f
      ON f.phone = s.phone AND f.first_d = s.d
  ) t
)
SELECT cr.massagist_id, DATE_FORMAT(f.first_d, '%Y-%m') AS first_month,
       SUM(cr.w) AS new_customers,
       SUM(CASE WHEN DATEDIFF(sv.second_d,f.first_d) BETWEEN 1 AND 30
                THEN cr.w ELSE 0 END) AS repurchase_30d,
       SUM(CASE WHEN DATEDIFF(sv.second_d,f.first_d) BETWEEN 1 AND 10
                THEN cr.w ELSE 0 END) AS repurchase_10d
FROM credit cr
JOIN first_visit f ON f.phone = cr.phone
LEFT JOIN second_visit sv ON sv.phone = cr.phone
GROUP BY cr.massagist_id, DATE_FORMAT(f.first_d, '%Y-%m');
```

说明：0 元有效服务不排除；`type=1` 购券不算到店，实际核销服务单进入统计。首单与二次到店必须基于全量有效到店寻找，不能为了筛某个月或某个伙伴，先裁掉历史/其他伙伴的记录。二次由谁服务不改变首单伙伴归属。

日期锚点按原文 `DATE(pay_time)`；实际部署统一门店业务时区。手机号规范化、同号归并与异常号码处理需在公共数据层一致完成，不能在前端自行去重。

老客统计：从 `services` 取 `d > first_d` 且在 R 窗口内的记录，为每条记录查全量 visits 中同 phone、`d` 之后最早到店。`COUNT(*)` 为分母，下一到店差 1–60 天为分子，按伙伴汇总。

10 天顺位明细从 `credit + first_visit + second_visit` 获取，过滤间隔 1–10 天；`ROW_NUMBER() OVER (PARTITION BY massagist_id, first_month ORDER BY second_d, phone)` 得到稳定整数位次。实际生产响应不下发排序用的明文手机号。

### 6.3 成就与项目认证映射

| 指标 | 规则 |
|---|---|
| 加入天数 | `DATEDIFF(today, COALESCE(entry_day, 本人全量首单日))+1`；均缺失时显示待维护，不制造加入日期 |
| 累计原始服务分钟 | valid join 有效明细，限定本人及轴内日期，SUM(duration)；不在已去重 services 上丢失不同项目实际分钟 |
| 服务客人数 | 同范围 COUNT(DISTINCT phone) |
| 头号粉丝 | 同范围按 phone 累计 duration 取第一；稳定处理同分钟并列，昵称与脱敏号由后端返回 |
| 项目认证次数 | 从 valid join 明细构造 DISTINCT phone,d,massagist_id,project_id 的项目服务集，再按认证表统计 |

认证统计设计片段（接在公共 valid CTE 后）：

```sql
, project_services AS (
  SELECT DISTINCT v.phone, v.d, od.massagist_id, od.project_id
  FROM valid v JOIN oms_order_detail od ON od.order_id = v.order_id
  WHERE od.state IN (1, 2) AND od.project_id IS NOT NULL
)
SELECT p.id, p.name AS project_name, c.cert_date,
       COUNT(s.phone) AS count_since_cert,
       SUM(CASE WHEN s.d > DATE_SUB(:axis_end, INTERVAL 30 DAY)
                THEN 1 ELSE 0 END) AS count_30d
FROM s_massagist_project_cert c
JOIN s_project p ON p.id = c.project_id
LEFT JOIN project_services s
  ON s.massagist_id = c.massagist_id AND s.project_id = c.project_id
 AND s.d > c.cert_date
 AND s.d BETWEEN :axis_start AND :axis_end
WHERE c.massagist_id = :me AND c.cert_date IS NOT NULL
GROUP BY p.id, p.name, c.cert_date
ORDER BY c.cert_date;
```

本版去除了旧 SQL 中“对应明细 project_id”的伪占位。两类次数均在所选轴范围、认证次日之后统计；近 30 天以轴终点回望并与轴范围取交集。

| `s_incentive_item` | 伙伴、归属月、类别、来源事件、weight、sequence_no、unit_price、amount、config_id、settlement_id、状态；类别×来源业务唯一键，防重计 |
| 原结算扩展 | 分类金额、总额、规则/统计快照引用、确认/发布状态与时间；不能只将所有新增项塞成无来源的 otherAmount |

正式规则发布应采用不可变 revision；同生效月修订也保留旧 revision，并明确哪些未确认估算可重算。原型同月保存替换活动配置并保留本地审计，只是交互演示，不等于完整生产账本。
