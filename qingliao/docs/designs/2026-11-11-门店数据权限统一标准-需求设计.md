# 门店数据权限统一标准（Shop Scope）需求设计

> 版本：v1.0　日期：2026-11-11　范围：PC 管理后台（tou-mall-admin-web）+ 后端（tou-mall-server/mall-admin）
> 目标：把"门店隔离"从"每个页面自己记得传"变成"框架默认收敛"，并一次性查漏补缺历史功能。

---

## 0. 一句话结论

后台目前只有一个域（激励）真正做了门店鉴权：86 个 controller 里仅 2 个调用过 `IncentiveAccessService`。
其余全部依赖"前端传 shopId、后端顺手过滤"，而 `WrapperBuilder.equal("shop_id")` 在参数为空时**不拼条件**，
所以**清空门店筛选框 = 看全公司数据**。本方案把授权收敛到服务端四层，前端下拉只做"请求范围"。

---

## 1. 授权模型（已定稿）

### 1.1 事实源

| 项 | 位置 | 说明 |
|---|---|---|
| 主门店 | `ums_admin.shop_id` | 账号默认门店 |
| 授权门店集合 | `ums_admin.shop_id_arr`（JSON 数组字符串） | 可为空 |
| 全局角色 | 配置 `shop.scope.global-roles`（默认沿用 `超级管理员,总助,运营,财务,admin`） | 可跨店、可看全量 |

### 1.2 三种范围（不再存在"空 = 全表"）

| 范围 | 判定 | 数据可见 | 下拉可选项 |
|---|---|---|---|
| `GLOBAL` | 账号角色命中全局白名单 | 全部门店 | 全部 + 具体门店 |
| `SCOPED` | 非全局，且 `authorizedShopIds` 非空 | 仅授权集合 | 仅授权门店，可多选/「全部门店（授权内）」 |
| `NONE` | 非全局且授权集合为空 | 无 | 空，页面提示"未配置门店" |

### 1.3 四条已确认的语义（本次拍板）

1. **受限账号不传门店 = 授权范围内的全部**（不是全表，也不是强制报错）。
2. **全局角色沿用配置白名单**，不靠 `shop_id_arr` 为空来推断（避免 fail-open）。
3. **客户 / 客户券 / 审批 = 集团级实体**，不做门店过滤，且**移除**这些页面上的门店筛选下拉（消除"已隔离"的错觉）。
4. **首页切换器 = 当前门店上下文**；页面内下拉可选「全部门店（授权内）」，清空即回到授权范围全部。

## 2. 七条硬规则

| # | 规则 | 反例（现存） |
|---|---|---|
| R1 | 客户端传入的 `shopId` 只是"请求范围"，必须与服务端授权求交，越界 403 | `/adminTodo/panel?shopId=任意` |
| R2 | 禁止"空 = 全表"。空值必须是"授权范围全部"，绝不降级全表 | `WrapperBuilder.equal("shop_id")`、`in("shop_id", 空集合)` |
| R3 | 门店归属表（有 `shop_id` 列）一律强制作用域；集团级表不得出现门店筛选 UI；跨店关系需源店+目标店双校验 | 客户页门店下拉；排班目标门店 |
| R4 | 读与写同等校验：拿到单条记录后必须 `assertAccess(entity.getShopId())` | `/order/info?id=`、`/bed/remove` |
| R5 | 门店字典唯一出口：`/shop/authorized`（授权内）+ `/shop/listAll`（仅全局） | 首页切换器用 `/shop/listAll` |
| R6 | fail-closed：解析失败/无授权一律拒绝，禁止降级为全量 | `resolveShopId` 在多处被绕过 |
| R7 | 新增接口必须登记到第 6 节矩阵，并附一条越权测试 | 无 |

## 3. 后端架构：四层收敛

```
请求 ──► L1 ShopScopeInterceptor     解析 shopId/shopIds → 校验 → ShopScope 存入 ThreadLocal
        │                            （非后台 admin 请求直接跳过，小程序链路不受影响）
        ├─► L2 BaseService.buildParams  实体有 shop_id 列 → 自动 in(shop_id, effective)
        ├─► L3 资源断言             service 内 assertAccess(entity.getShopId()) / @ShopScoped AOP
        └─► L4 字典接口             /shop/authorized、/shop/listAll、/shop/list
```

### 3.1 L1 拦截器

- 位置：`com.macro.mall.component.ShopScopeInterceptor`，注册于 `ShopScopeWebConfig`。
- 生效条件：`SecurityContextHolder` 的 principal 是 `AdminUserDetails`（后台账号）。否则跳过（小程序/公开接口）。
- 解析参数：`shopId`（单店）、`shopIds`（多店，逗号或重复参数）。
- 校验：`SCOPED` 账号传入未授权门店 → `BusinessException("无权查看该门店")`。
- 结果：`ShopScope{global, authorizedIds, requestedIds}` 存 `ShopScopeHolder`，请求结束 `remove()`。
- 同请求内缓存：`shop.scope.cache-request=true`，避免多次查角色。

### 3.2 L2 基类自动作用域（关键改造）

`BaseService.buildParams` 是所有 `page / listByPage / listNoPage` 的唯一入口，在此处兜底：

```java
protected QueryWrapper<T> buildParams(Map<String, Object> params) {
    QueryWrapper<T> qw = new QueryWrapper<>();
    if (params != null) buildWrapper(humpToLine(params), qw);
    applyShopScope(qw, params);   // 新增：实体含 shopId 字段才生效
    ...
}

private void applyShopScope(QueryWrapper<T> qw, Map<String, Object> params) {
    if (shopIdFieldAbsent()) return;                    // 集团级实体：不处理
    ShopScope scope = ShopScopeHolder.current();
    if (scope == null || scope.isGlobal() && scope.getRequestedIds() == null) return;
    if (scope.isGlobal()) return;                        // 全局角色自由查
    List<Long> ids = scope.effectiveIds();               // 请求范围 ∩ 授权
    if (ids.isEmpty()) throw new BusinessException("当前账号尚未配置可查看门店");
    qw.in("shop_id", ids);
}
```

- 判定"实体是否门店归属"：`TableInfoHelper.getTableInfo(getEntityClass())` 含 `shopId` 属性，结果按 Class 缓存。
- 与子类已有的 `.equal("shop_id")` **兼容且不双写**：子类条件已存在时，L2 用 `and(w -> w.in(...))` 追加不可绕过的 `in`，
  等价于"取交集"，即使子类写错也不会放宽。
- 逃生口：`params.put("ignoreShopScope", true)`，**仅限**明确评审过的集团级列表，
  并在第 6 节矩阵中登记原因（本期未引入注解，避免与 AOP 增强叠加造成隐式放行）。

### 3.3 L3 资源级断言

```java
// service 内，读写一致（已内置，无需手写）
Order order = getById(id);      // 越界直接抛「无权访问该门店的数据」
order.setComment("x");
updateById(order);              // 写侧同样校验
```

实现位置：`BaseService` 覆写 `getById / listByIds / save / saveBatch / updateById / removeById`，
覆盖全部继承 `BaseService` 的门店归属实体（21 张表）。业务代码**不需要**再逐个接口写 `assertAccess`，
新增接口只要走这几个入口即自动受保护；若要绕过必须有 `SHOP_SCOPE_ENFORCE=false` 或明显评审记录。

### 3.4 L4 字典接口

| 接口 | 改造后语义 |
|---|---|
| `GET /shop/authorized` | 新增。返回当前账号可管理/可查看的门店（全局=全部），带 `isMain` 标记。**前端所有门店下拉唯一数据源** |
| `GET /shop/listAll` | 收紧：非全局角色返回其授权门店（不再全量） |
| `GET /shop/list` | 保持：授权门店（已有） |
| `GET /admin/info` | 增加 `authorizedShopIds`、`isGlobal`，供前端决定是否显示「全部门店」选项 |

## 4. 前端标准

### 4.1 组件

| 组件 | 职责 | 规则 |
|---|---|---|
| `ShopSelector`（改造） | 页面筛选/表单门店选择 | 数据源 `api.shop.authorized`；`v-model` 为空 = 授权范围全部；`allowAll` 时多出"全部门店"选项；**不再默认写入全局 shopId** |
| `GlobalShopSwitcher`（新增，首页） | 全局当前门店 | 复用同一接口；多店账号才有「全部门店」；单店账号隐藏 |
| `utils/shopScope.js`（新增） | 统一参数注入 | `allShops=0` 哨兵值在发请求前被剔除，等价于"不传" |

### 4.2 三条前端规则

1. 门店下拉**只允许**从 `getters.authorizedShopList` 取数，禁止直接调用 `listAll`。
2. 页面默认值 = 全局当前门店（`getters.shopId`），用户清空后**传空**，由后端收敛为授权范围。
3. 集团级页面（客户、客户券、审批）删除门店下拉与 `shopId` 参数。

### 4.3 现存需清理的写法

- `views/home/index.vue:19` 用 `shopListAll` → 改 `authorizedShopList`。
- 12 处 `dispatch('setShopAllList')` → 改为 `setAuthorizedShopList`（保留旧 action 名做别名，避免一次性全改）。
- `views/order/OrderList.vue:5` 等 24 处 `shop-selector` 的 `clearable` 保留，但语义从"清空=全量"变为"清空=授权内全部"。

## 8. 验收用例

| # | 场景 | 期望 |
|---|---|---|
| 1 | 店长（授权 A）打开订单列表，不选门店 | 只见 A 门店订单 |
| 2 | 店长清空门店筛选 | 仍是 A 门店订单（不再全量） |
| 3 | 店长手动改 URL `?shopId=B` | 403 "无权查看该门店" |
| 4 | 店长打开首页切换器 | 只列 A（单店时切换器隐藏） |
| 5 | 运营（全局）打开首页切换器 | 列全部 + 「全部门店」 |
| 6 | 运营选「全部门店」 | 看到全公司汇总 |
| 7 | 店长 `/order/info?id=他家订单` | 403 |
| 8 | 店长打开客户页 | 无门店下拉（集团级） |
| 9 | 未配置门店的新账号 | 列表 403 "当前账号尚未配置可查看门店" |
| 10 | 小程序端预约时间接口 | 行为不变（L1 跳过） |

### 8.1 写路径专项验收（`save`/`updateById` 新校验最可能误伤的三条链路）

前置：测试环境两台设备，分别登录 **店长(A)** 与 **总部运营(全局)**；准备 A、B 两家门店数据。

| # | 链路 | 操作 | 期望 | 若失败怎么判 |
|---|---|---|---|---|
| W1 | 下单 | 店长(A) 新建产品订单（PC 下单/接待下单各一次） | 200；`SELECT shop_id FROM s_order ORDER BY id DESC LIMIT 1` = A | 403「无权访问该门店的数据」→ 前端 DTO 未带 shopId 或带了 B |
| W2 | 下单-编辑 | 店长(A) 打开该订单改备注后保存 | 200；`shop_id` 仍为 A（不得变 NULL） | `shop_id` 变 NULL → 前端编辑表单未回填 shopId |
| W3 | 排班 | 店长(A) 批量排班（`POST /massagistSchedules/batchAdd`，body 带 `shopId=A`） | 200；`s_massagist_schedules.shop_id = A` | 403 → 校验取错了字段 |
| W4 | 调店 | 店长(A) 把 A 店疗愈师临时调到 B 店（`/massagistSchedules/saveTargetShop`） | 200；记录 `shop_id=A`、`target_shop_id=B` | 403 → 说明校验误用了 `targetShopId`（当前实现只校验 `shopId`，不应失败） |
| W5 | 礼品卡生成 | 运营在 A 活动下生成 10 张卡（`POST /giftCard/batch/save`） | 200；`s_gift_card.shop_id = A` | 403 → 活动 `shop_id` 与操作人授权不一致，需确认活动归属 |
| W6 | 礼品卡发放 | 店长(A) 单张发放 + 批量发放（`/giftCard/distribution`、`/batch/distribution`） | 200；状态 TO_BE_RECEIVED | 403 → 说明取到的卡不属于 A |
| W7 | 礼品卡越权 | 店长(A) 对他店卡 id 调 `/giftCard/distribution` | 403「无权访问该门店的数据」 | 200 → 校验未生效 |
| W8 | 排班越权 | 店长(A) 用 body `shopId=B` 调 `/massagistSchedules/batchAdd` | 403 | 200 → `saveBatch` 校验失效 |

排查顺序：先看响应 message 是否为「无权访问该门店的数据」（说明是 L2/L3，不是业务异常），
再看 `[SHOP_SCOPE]` 关键字日志（enforce=false 时会打印实体名与 shopId）。
临时回滚：`SHOP_SCOPE_ENFORCE=false` 重启，全部降级为只记录日志。

## 9. 存量影响与灰度

- **行为变化**：清空门店筛选从"全量"变为"授权内全部"，店长类账号首次上线会看到数据变少——这是修复，不是回归，需在发布说明中标注。
- **灰度**：`shop.scope.enforce=false` 可整体回退到旧行为（仅记录日志 `[SHOP_SCOPE]`，不拦截），
  观察 3 天日志里"将被拦截"的调用是否都是误伤，再切 `true`。
- **回滚**：拦截器 + L2 均为新增代码，回滚只需关闭开关；无 DDL 变更。
- **无数据迁移**：不改表结构，不改 `shop_id_arr` 格式。

## 10. 明确不做

- 不做 MyBatis 租户插件式行级隔离（现有 SQL 关联复杂，误伤面大于收益）。
- 不把客户改成"归属门店"模型（业务上客户跨店消费，第 1.3 节已定集团级）。
- 不改小程序端既有接口语义（L1 只对后台 admin 生效）。

| 1 | 异步线程（`ppzAsync`/`CompletableFuture`）丢失 `ShopScopeHolder` | 异步内查询不受限 | 异步路径显式传 shopIds；后续用 TTL 包装线程池（mall-admin 已有 transmittable-thread-local 依赖） |
| 2 | `PayoutService` / `StatisticsService` 自定义 SQL（payoutpage、topAlldata、薪资、服务时长） | 依赖前端传 `shopIdArrNew` | 已在 controller 层用 `restrictShopIdArray` 求交；SQL 内部仍需型检 |
| 3 | 门店主数据页 `/shop/page`、`/shop/saveOrUpd`、`/shop/remove` | 受限账号可看到全部门店并可改 | 需产品决定"门店主数据是否仅总部可维护"，再定是否 `requireGlobal` |
| 4 | `IncentiveAccessService` 与 `ShopScopeService` 各有一套全局角色解析 | 配置漂移风险 | 下一步让激励域委托 `ShopScopeService`（默认值已对齐 `incentive.global-roles`） |
| 5 | 首页切换器「全部门店」 | 未提供聚合视图 | 需 `shopId=0` 哨兵 + 请求层剔除 + 各页 `if(!shopId) return` 守卫逐个适配，建议单独立项 |
| 6 | `getOne(wrapper)`、`baseMapper.selectById` 等直接走 mapper 的路径 | 绕过 IDOR 校验 | 已用 grep 确认主要读写入口走 `getById/updateById/removeById/save`；后续新增代码禁止直连 mapper 读单条 |

### 13.1 这台机器上踩过的三个坑（脚本已堵住）

1. **边跑边就地 `mvn package`** → 运行中的 JVM 懒加载类失败，报 `NoClassDefFoundError: ModelAndViewDefiningException`，表现为随机接口 500（本轮实测 `/shop/list` 500 就是这个原因）。脚本改为**先停应用再打包**。
2. **`kill` 杀不掉旧进程**（`-Dfullyu.test-mode` 下 SIGTERM 不生效）→ 两个 JVM 同时跑，定时任务重复执行。脚本 TERM 等 15s 后 `kill -9`，并断言只剩 1 个实例。
3. **`pgrep -f` 会匹配到执行命令的 shell 自己**，导致误杀/误判。脚本用 `java .*mall-admin-1.0-SNAPSHOT.jar` 精确匹配。

另外：这台机器上有 Jenkins（job：`Full愈大会员后端部署`/`Full愈大会员管理端前端部署`）。如果有 GitHub 触发的流水线在跑，会与本脚本**同时改同一个 jar**，发布前先确认没有正在跑的构建。

### 13.3 无数据库变更

本期没有建表/加字段，`tou_mall_test` 不用动。

### 13.4 开关：默认**不拦截**

`application.yml` 里 `shop.scope.enforce` 默认已是 `false`，含义：

| 生效 | 不生效（只打日志） |
|---|---|
| L2 列表/统计按授权门店过滤、L4 门店下拉收敛 | L1 入参越界拦截、L3 按 id 读写拦截 |

也就是**数据隔离照常工作，但不会有人被 403 卡住**，这是当前阶段想要的形态。日志前缀 `[SHOP_SCOPE]`，想看谁会被拦：`grep '[SHOP_SCOPE]' 日志`。

要开硬拦截：`SHOP_SCOPE_ENFORCE=true` 重启，不用改代码。
