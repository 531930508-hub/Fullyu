> 第 14 节是实跑与修复记录；DDL 与 dist 的发布步骤见 `release-2026-11-16-月度发券规则.md`。

## 0. 一句话

在现有「自动发券规则」上加一种 **monthly** 类型：指定券模板 + 人群（全部注册用户 / 全部年卡会员）+ 触发日（1–28），到点自动发放，后台随时可手动触发、当月可补发、跨月不补；2 万人以上分批发完，中断可续，同月绝不重发。

## 1. 功能契约（模板 A）

```text
功能编号/名称：COUPON-MONTHLY｜月度发券规则
业务目的与使用角色：总部运营按月给全部注册用户或全部年卡会员发固定代金券（月度福利/唤醒），在后台「自动发券规则」页配置与执行。
本次范围：新增 monthly 规则类型 + 执行记录表 + 异步分批执行 + 后台规则页扩展。
明确不做：不做推送通知；不做按门店/标签细分；不改生日/新客/沉睡三类规则的行为；不改券模板与核销；不改小程序顾客端；不做中途取消与已发作废。
原有基线：「自动发券规则」页（新建/试算/立即执行/启停/删除）、批量发放（全部/普通/年卡 + 注册日期，上限 5000）、批次与作废。

经营规则：
- 正常结果：每个符合条件的顾客每个自然月恰好一张；同一券模板同月只产生一个批次。
- 失败结果：执行停在断点，保留游标与已发记录，界面可见并以「继续执行」恢复；已发券不自动回收。
- 禁止结果：同月重复发放；定时器未开却显示"已自动发放"；失败伪装成功；把无手机号顾客计入发放数。
- 钱/数量/日期/归属口径：券面额与有效期由券模板决定（validDays 或固定区间）；周期为上海时区自然月 YYYY-MM；归属记 ruleId + rulePeriod + batchId。
- 需用户决策项：均已确认（见第 2 节），无遗留经营决策。

多端影响：
- 总部入口：admin「自动发券规则」页；执行记录接口。
- 门店入口：无（券为总部发放，门店只核销）。
- 顾客端：无改动；会员中心「我的权益」自然可见。
- 后台任务/对账：调度器创建 run；批次列表可查；run 与 batch 双向可达。

接口：见第 5 节。授权：coupon:view 只读，coupon:manage 写。持久化：coupon_rules（已有）＋ coupon_rule_runs（新增）＋ coupon_batches / customer_coupons（已有，不改结构）。
配置：规则级 dayOfMonth/tier/couponId 与「自动执行」开关（enabled）总部可改；环境级 COUPON_RULES_ENABLED 只做全局紧急停止（设 0 全停），COUPON_RULE_HOUR 只影响日常规则整点；手动执行不受两者影响。
状态机：pending → running → succeeded／failed；failed 可续跑。
并发与幂等：(ruleId, period) 唯一 + 租约 claimedAt + (ruleId, customerId, rulePeriod) 唯一 + 页内差集重查。
外部结果未知：无外部支付/CRM 写操作；仅读 CRM 快照字段，读取失败沿用本地快照（现状）。
本地草稿：不适用（无前端草稿）。
日志：创建/编辑/启停/删除/手动执行写 logAction；run 记录 operatorId/operatorName（系统执行记 system）。
迁移与部署：新增表 1 张（纯加法）；生产 DDL 需授权；server + admin 需发布；开关需单独授权。
```

## 2. 已确认口径

| 项 | 结论 |
|---|---|
| 触发方式 | 到点自动 + 后台手动触发/当月补跑 |
| 人群 | 全部用户 = 有手机号的注册顾客；全部会员 = 有效年卡（`memberTier='annual'` 且 `memberUntil` 空或未过期） |
| 旧券未用 | 不阻挡，每月每人一张 |
| 有效期 | 沿用券模板（`validDays` 或固定区间），规则不新增有效期字段 |
| 触发日 | 1–28 |
| 漏跑 | 当月内可补，跨月不补 |
| 防重复 | 同一券模板只允许一条启用中的月度规则（服务层校验） |
| 改券 | 可改，下月生效，当月已发不回滚 |
| 通知 | 不做推送 |
| 发送时刻 | 默认 10:00 起（沿用 `COUPON_RULE_HOUR`） |
| 规则删除 | 有执行记录则禁止物理删除，只能停用 |
| 失败处置 | 只能「继续执行」或停用规则；不提供 partial 结束与已发作废 |
| 规模 | 2 万人以上，必须分批、可续 |

## 3. 数据模型

### 3.1 `coupon_rules`（复用，仅扩枚举）

- `kind='monthly'`
- `config={"dayOfMonth":1}`，1–28
- `tier` 仅 `all|annual`；`standard` 拒绝
- `couponId` 可改；`enabled` 停用只阻止新 run

### 3.2 `coupon_rule_runs`（新增）

```prisma
model CouponRuleRun {
  id           String    @id
  ruleId       String    @map("rule_id")
  couponId     String    @map("coupon_id")   // 本月锁定的券模板快照
  tier         String    @default("all")     // 本月锁定的人群口径
  period       String                        // YYYY-MM（上海时区）
  trigger      String    @default("auto")    // auto | manual
  status       String    @default("pending") // pending | running | succeeded | failed
  targetCount  Int       @default(0) @map("target_count")
  issued       Int       @default(0)
  skipped      Int       @default(0)
  cursor       String?                       // 最后处理到的 customer.id
  batchId      String?   @map("batch_id")
  attempts     Int       @default(0)
  lastError    String    @default("") @map("last_error")
  claimedAt    DateTime? @map("claimed_at")  // 执行租约，超 5 分钟可接管
  startedAt    DateTime? @map("started_at")
  finishedAt   DateTime? @map("finished_at")
  operatorId   String?   @map("operator_id")
  operatorName String    @default("") @map("operator_name")
  createdAt    DateTime  @default(now()) @map("created_at")

  rule   CouponRule @relation(fields: [ruleId], references: [id], onDelete: Restrict)
  coupon Coupon     @relation(fields: [couponId], references: [id], onDelete: Restrict)

  @@unique([ruleId, period])
  @@index([status, claimedAt])
  @@index([period])
  @@map("coupon_rule_runs")
}
```

设计要点：

- `couponId` / `tier` 在 run 上快照，保证"改券下月生效"与执行期间口径稳定。
- `cursor` 按 `customer.id` 升序翻页，不用 offset。
- `claimedAt` 是租约不是锁；正确性靠唯一索引兜底。
- `onDelete: Restrict`：审计不断链。

### 3.3 不改的表

- `customer_coupons`：`(ruleId, customerId, rulePeriod)` 唯一索引即月度去重落点，`rulePeriod='YYYY-MM'`。
- `coupon_batches`：一次月执行 = 一个批次，`requestKey=rule:{ruleId}:{YYYY-MM}`，`source='auto'`。

### 3.4 迁移

- 开发：`apps/server/prisma/migrations/<ts>_coupon_monthly_rule_run/migration.sql`（SQLite 方言，纯新增）。
- 生产：`deploy/mysql/20261116-coupon-monthly-rule-run.sql`（手写 MySQL DDL，只 CREATE TABLE + 索引，不动已有表）。
- 「同券仅一条启用月度规则」无部分唯一索引可用，落在服务层事务内复查；并发窗口极小，接受并记录。

## 4. 执行流程与状态机

### 4.1 触发判定（每 10 分钟一轮）

```text
上海时间 hour >= COUPON_RULE_HOUR
且 今日 >= 规则.dayOfMonth
且 本月无 succeeded 的 run
→ 创建/领取 run 并异步执行
```

- 不依赖"正好撞上 10:00 那一轮"，进程晚起也能当月补发。
- 生日/新客/沉睡规则时序不变。
- 手动执行走同一入口，`trigger='manual'`，允许早于触发日。

### 4.2 状态机

| 状态 | 含义 | 允许迁移 |
|---|---|---|
| pending | 已建未跑 | → running |
| running | 持租约执行中 | → succeeded / failed；租约超 5 分钟可被接管 |
| succeeded | 全部处理完，批次计数已回写 | 终态（同月不再触发，手动返回 409） |
| failed | 停在断点，cursor 保留 | attempts<5 自动重试；否则人工「继续执行」 |

失败分类：

- 可重试：数据库超时/连接中断 → 自动重试续跑。
- 不可恢复：券停用/过期、规则停用 → 立即 failed，写 lastError，不再重试。

### 4.3 分批写入

1. `customer.findMany`（`id > cursor`，take 500，`phone != null`；annual 时加 `memberTier='annual'` 且 `memberUntil` 空或 > now）
2. 页内查已存在的 `(ruleId, customerId, rulePeriod)`，差集为待发
3. `createMany` 落库（不用 `skipDuplicates`，跨库行为不一致）；唯一键冲突按整页重查一次
4. 同事务更新 `cursor`/`issued`/`skipped`/`claimedAt`

2 万人 ≈ 40 页，每页 3 条 SQL；单页失败不影响已提交页。

### 4.4 批次归因

- 首次落库创建 `CouponBatch`，执行过程中不逐条累加，结束时按 `count(customer_coupons where batchId)` 回写 `issued/skipped/requested`。
- 中途失败显示"部分发放"，以 run 为准。
- 跨月运行一律用 `run.period`，不用 `now`。

## 7. 边界与异常

| 场景 | 行为 |
|---|---|
| 券执行前停用/过期 | 不建 run，红字提示 |
| 执行途中券停用 | 当前页后停止，failed/COUPON_INACTIVE，已发保留 |
| 规则停用 | 进行中跑完；次月不触发 |
| 月中改券/人群/日期 | 仅影响之后新建的 run |
| 未到触发日手动发 | 允许；本月不再自动发 |
| 本月 succeeded 再点 | 409 ALREADY_DONE |
| 失败 >5 次 | 停止自动重试，人工续跑 |
| 无手机号顾客 | 不在范围，预览单列人数 |
| 年卡快照滞后（5 分钟 TTL） | 可能个别多/少发，接受并记录 |
| 已持有同款未用券 | 仍发，当月可能两张 |
| 跨月运行 | 按 run.period 写入 |
| 多实例/重复点击 | 租约 + 双重唯一键 |
| 券模板删除 | 无删除接口（只有启停），外键不会悬空 |

## 10. 验收规则（先定义）

- 正常：2 万注册顾客执行一次 → 每人恰好一张，批次一条，run succeeded，`issued` == 持券数。
- 非默认：触发日 15；人群 annual；提前手动发；`COUPON_RULE_HOUR=8`。
- 范围负向：年卡过期当天排除；无手机号排除；本月新注册本次不纳入。
- 重启：执行中重启，续跑不重发。
- 异常：某页抛错 → failed 且 cursor 保留；券停用 → 不无限重试；并发点击 → 409；双实例 → 单租约。
- 历史：跨月运行归上月；同月不重发。
- 真实/模拟界限：本地 SQLite 合成数据只算 E1；生产真实规模与真实到点属 E3/E4。

## 14. 集成测试怎么跑（2026-11-16 补）

时叙在 `42f5c09` 切 MySQL 后，`test/global-setup.ts` 原来只会造 SQLite 模板库（`DATABASE_URL=file:…`），Prisma 直接报 `P1012`，**全部 spec 都跑不起来**。已按迁移方案「交付物 6」补齐 MySQL 分支：

- `test/global-setup.ts`：设了 `TEST_DATABASE_URL=mysql://…` 就走 MySQL——校验库名必须含 `_test` 或 `rehearsal`（防 `--force-reset` 误伤生产）→ `prisma db push --force-reset` 建结构 → 灌 `prisma/seed.ts`；指针文件写成 `mysql:<url>`。不设则维持原来的 SQLite 模板库逻辑。
- `src/testing/harness.ts`：读指针；MySQL 模式下每个 spec 复制一个独立库（`CREATE DATABASE teahour_test_run_<pid>_<seq>` + 逐表 `CREATE TABLE … LIKE` / `INSERT … SELECT`，等价于 SQLite 复制 `.db`），`close()` 时 `DROP DATABASE`。比「清表 + 重灌种子」快一个数量级（种子是几百次往返，走 SSH 隧道要 13s）。SQLite 模式仍是复制模板库。

测试库：121.40 上的 `teahour_test`（utf8mb4，独立于生产 `teahour`），账号 `teahour_test` 只授 `teahour_test` / `teahour_test_%`。

```bash
# 本机没有 MySQL：走 SSH 隧道连测试库，再跑 jest
ssh -f -N -L 3307:127.0.0.1:3306 mall-test
cd shixu/apps/server
TEST_DATABASE_URL="mysql://teahour_test:<pw>@127.0.0.1:3307/teahour_test" npx jest
```

注意：这个库会被 `--force-reset` 与每个 spec 的复制库反复覆盖，**只能放测试数据**；密码不进仓库，需要时从 121.40 `/etc/teahour/api.env` 之外单独管理。

### 14.2 12 条失败的修复（2026-11-18）

逐条按「事务内快照读 / TEXT 上限 / 加锁顺序」三类根因修，全部先确认红了再改绿：

| # | 问题 | 修法 |
|---|---|---|
| 1 | `work_settlements.lines_json` 是 TEXT（64KB） | schema 改 `@db.LongText` + 迁移 `20261118120000_settlement_lines_longtext`；新增回归用例（700 段 ≈80KB，TEXT 下必红） |
| 2 | `markPaid` 后到者用事务内快照读定性 | MySQL 默认 REPEATABLE READ，事务内看不到并发赢家已提交的状态，会把「重复回调」误判成「迟到支付」返回 `blocked-cancelled`。改为 `updateMany` 抢不到就让事务结束，**事务外**新快照回读再定性（paid→`duplicate`，cancelled→补留痕+`blocked-cancelled`） |
